

> [!summary] Определение  
> **Threat model** — описание того, что мы защищаем, как устроена система, что может пойти не так и какими проверяемыми мерами мы снижаем риск.

Threat modeling выполняют до атаки и обновляют при изменении архитектуры.

## Основные элементы

|Элемент|Вопрос|Пример Marketplace|
|---|---|---|
|Assets|Что имеет ценность?|Аккаунты, ledger, товары, персональные данные|
|Actors|Кто взаимодействует с системой?|Buyer, seller, admin, CI/CD, злоумышленник|
|Entry points|Откуда приходят данные?|HTTP API, WebSocket, загрузка файлов, Kafka consumer|
|Data flows|Как движутся данные?|Browser → API → PostgreSQL|
|Trust boundaries|Где меняется уровень доверия?|Интернет → reverse proxy; API → broker|
|Threats|Что может пойти не так?|Подмена пользователя, изменение ledger, DoS|
|Mitigations|Что снижает риск?|AuthN/AuthZ, idempotency, audit log, rate limit|
|Verification|Как доказать работу защиты?|Tests, Burp, review конфигурации, alert|

## Scope сначала

Без границ threat model превращается в бесконечный список.

Пример scope:

```
В scope:
- регистрация и вход;
- создание и изменение товара;
- покупка и уведомление продавца;
- FastAPI, PostgreSQL, Redis, Kafka.

Не в scope:
- безопасность устройства пользователя;
- внутренняя реализация платёжного провайдера;
- физическая безопасность дата-центра.
```

## Data Flow Diagram

Начинай не с названий уязвимостей, а с движения данных и границ доверия.

```
flowchart LR
    U["Browser"] -->|"HTTPS"| A["Marketplace API"]
    A -->|"SQL"| D[("PostgreSQL")]
    A -->|"Events"| K["Kafka"]
    K --> W["Notification worker"]
```

Типичные границы доверия:

- интернет ↔ reverse proxy;
    
- reverse proxy ↔ API;
    
- API ↔ база / брокер;
    
- один микросервис ↔ другой;
    
- CI/CD ↔ production cluster.
    

## STRIDE

STRIDE помогает систематически задавать вопросы для каждого элемента и потока.

|   |   |   |   |   |
|---|---|---|---|---|
|Буква|Угроза|Вопрос|Пример|Защита|
|S|Spoofing|Можно ли выдать себя за другого?|Украденная session cookie|MFA, безопасные sessions, rotation|
|T|Tampering|Можно ли незаметно изменить данные?|Изменение суммы заказа|Server-side calculation, constraints, signatures|
|R|Repudiation|Можно ли отрицать действие?|Admin отрицает удаление товара|Audit log с actor и timestamp|
|I|Information Disclosure|Можно ли прочитать чужое?|Seller получает чужой заказ|Ownership checks, минимальный response|
|D|Denial of Service|Можно ли лишить сервис доступности?|Flood `/login` или WebSocket|Rate limit, quotas, timeouts, backpressure|
|E|Elevation of Privilege|Можно ли получить лишние права?|Seller вызывает admin endpoint|Backend AuthZ, least privilege, RBAC|

> [!note]  
> STRIDE не заменяет опыт и тестирование. Это checklist, который помогает не забыть классы угроз.

## Повторяемый процесс

1. Определить scope и цели безопасности.
    
2. Найти assets, actors и entry points.
    
3. Нарисовать компоненты, data flows и trust boundaries.
    
4. Применить STRIDE к компонентам и потокам.
    
5. Описать реалистичный attack path.
    
6. Оценить вероятность и ущерб.
    
7. Назначить owner, mitigation и способ проверки.
    
8. Зафиксировать остаточный риск.
    
9. Обновлять модель при изменении архитектуры.
    

## Карточка угрозы

```
### TM-API-003: Изменение чужого товара

- Asset: товары продавцов
- Entry point: PATCH /api/v1/catalog/products/{id}
- Предусловие: атакующий вошёл как seller
- Attack path: передаёт ID чужого товара
- Результат: изменяет цену или описание другого seller
- Вероятность: высокая без ownership check
- Ущерб: высокий
- Mitigation: проверка product.seller_id == current_user.id
- Verification: integration test + ручной запрос через Burp
- Owner: backend
- Status: mitigated
```

## Пример: покупка товара

|   |   |   |   |
|---|---|---|---|
|Шаг|Угроза|Мера|Проверка|
|Client отправляет product ID|Подмена цены в body|Цена берётся из БД|Изменить цену в Burp|
|API списывает баланс|Повтор одного запроса|Idempotency key + transaction|Повторить запрос|
|API пишет order|Частичная запись|Transaction / Unit of Work|Имитировать ошибку|
|Event уходит в Kafka|Дублирование сообщения|Idempotent consumer|Доставить событие дважды|
|Seller получает notification|Утечка чужих данных|Минимальный payload + ownership|Проверить другого seller|

## Оценка риска без ложной точности

Для учебного проекта достаточно качественной матрицы:

|   |   |   |   |
|---|---|---|---|
|Вероятность / Ущерб|Низкий|Средний|Высокий|
|Низкая|Low|Low|Medium|
|Средняя|Low|Medium|High|
|Высокая|Medium|High|Critical|

Приоритет определяет не только балл. Учитывай доступность атаки, ценность asset, масштаб пользователей и возможность обнаружения.

## Частые ошибки

- начинать со списка OWASP, не нарисовав архитектуру;
    
- считать firewall единственной границей доверия;
    
- описывать только угрозу без mitigation и проверки;
    
- писать «использовать encryption» без указания данных, места и ключей;
    
- считать внутренний микросервис автоматически доверенным;
    
- не обновлять модель после появления Kafka, WebSocket или нового admin endpoint.
