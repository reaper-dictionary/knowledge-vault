

> [!summary] Главная идея  
> Пароли нельзя хранить в открытом или обратимо зашифрованном виде. Backend хранит результат медленной password-hashing функции и отдельно защищает endpoint входа от онлайн-атак.

## Hash, salt и pepper

### Password hash

Password hashing — одностороннее и намеренно затратное преобразование пароля. Для новых систем обычно выбирают Argon2id с параметрами, подходящими инфраструктуре.

```
пароль + уникальная salt → Argon2id → password hash
```

Backend проверяет пароль, повторяя вычисление с сохранёнными параметрами.

### Salt

**Salt** — уникальное случайное значение для каждого пароля.

Она:

- не обязана быть секретной;
    
- хранится вместе с хешем;
    
- не даёт одинаковым паролям иметь одинаковые хеши;
    
- делает заранее подготовленные таблицы менее полезными.
    

Современные библиотеки обычно создают salt и включают её в строку хеша автоматически.

### Pepper

**Pepper** — дополнительный секрет приложения, общий для множества паролей и хранящийся отдельно от БД, например в secret manager.

Pepper может усложнить атаку при краже только базы, но добавляет управление секретом и процедуру ротации. Он не заменяет Argon2id, salt и сильные пароли.

## Почему не обычный быстрый hash

`SHA-256(password)` считается плохим password storage: быстрый алгоритм позволяет перебирать огромное количество вариантов.

Нужна функция, специально созданная для паролей:

- Argon2id — основной современный выбор;
    
- scrypt — допустимая альтернатива;
    
- bcrypt — распространённый legacy-вариант с ограничениями;
    
- PBKDF2 — используется там, где этого требуют совместимость или стандарты.
    

> [!warning]  
> Конкретные параметры нельзя копировать вслепую. Их подбирают и периодически пересматривают с учётом задержки входа и доступных ресурсов.

## Офлайн- и онлайн-атаки

|Атака|Где выполняется|Что защищает|
|---|---|---|
|Офлайн-перебор|По украденной базе хешей, без запросов к серверу|Argon2id, уникальная salt, сильные пароли, pepper при подходящей модели угроз|
|Онлайн-перебор|Через работающий `/login`|Rate limit, задержки, MFA, мониторинг, временные ограничения|

Rate limit не защищает украденную базу хешей: при офлайн-атаке backend вообще не участвует.

## Типы онлайн-атак

|   |   |
|---|---|
|Атака|Схема|
|Brute force|Много паролей для одного аккаунта|
|Password spraying|Несколько популярных паролей для множества аккаунтов|
|Credential stuffing|Украденные пары логин–пароль с других сайтов|

Один лимит «по IP» недостаточен: атакующий распределит запросы. Один лимит «по аккаунту» позволяет блокировать чужих пользователей.

Нужна комбинация сигналов:

```
IP + аккаунт + устройство/сессия + скорость + история неудач
```

## Защита endpoint входа

- ограничение скорости по IP и аккаунту;
    
- увеличивающаяся задержка после неудач;
    
- короткая временная блокировка вместо постоянной;
    
- MFA, особенно для администраторов;
    
- обнаружение credential stuffing и аномалий;
    
- уведомление пользователя о подозрительном входе;
    
- отзыв сессий после компрометации;
    
- журналирование событий без записи паролей и токенов.
    

> [!danger] Не создавать DoS на логине  
> Постоянная блокировка после нескольких ошибок позволяет злоумышленнику намеренно блокировать чужие аккаунты.

## User enumeration

Небезопасные ответы:

```
«Пользователь не существует»
«Пароль неверный»
```

Они помогают собрать список зарегистрированных адресов. Безопаснее единый ответ:

```
«Неверный логин или пароль»
```

Нужно уменьшать и временную разницу. Для отсутствующего пользователя backend может выполнить фиктивную проверку заранее подготовленного password hash, чтобы путь обработки был похож на обычный.

> [!note]  
> Полностью скрыть все различия трудно: регистрацию и восстановление пароля тоже нужно проектировать с учётом enumeration.

## Смена и восстановление пароля

- токен восстановления должен быть случайным, одноразовым и короткоживущим;
    
- в БД лучше хранить его hash, а не исходное значение;
    
- после смены пароля старые reset-токены инвалидируются;
    
- для чувствительных аккаунтов отзываются активные sessions / refresh tokens;
    
- событие отправляется пользователю по независимому каналу;
    
- endpoint восстановления также защищается rate limit.
    

## Минимальный checklist

- Пароли хешируются специализированной password-hashing функцией.
    
- Для каждого пароля используется уникальная salt.
    
- Параметры hashing можно обновлять при следующем успешном входе.
    
- `/login`, registration и password reset имеют rate limit.
    
- Ответы входа не раскрывают существование аккаунта.
    
- Есть MFA для привилегированных ролей.
    
- Пароли, reset-токены и session ID не попадают в логи.
    
- Смена пароля инвалидирует старые recovery-токены.
