

> [!summary] Коротко  
> HTTP описывает запросы и ответы приложения. HTTPS — это HTTP внутри защищённого TLS-соединения. TLS шифрует трафик, проверяет его целостность и помогает клиенту проверить подлинность сервера.

## Выучить

- **HTTP-запрос** состоит из метода, адреса ресурса, заголовков и необязательного тела.
    
- **HTTP-ответ** состоит из статус-кода, заголовков и необязательного тела.
    
- **HTTP-метод** описывает намерение клиента: получить, создать, изменить или удалить ресурс.
    
- **HTTP stateless** означает, что каждый запрос самодостаточен; протокол не требует от сервера помнить предыдущие запросы.
    
- **Cookie** — значение, которое браузер хранит и автоматически отправляет подходящему сайту.
    
- **HTTPS** — HTTP, передаваемый внутри TLS.
    
- **TLS** обеспечивает конфиденциальность, целостность и аутентификацию сервера.
    
- **Сертификат** связывает имя хоста с публичным ключом и цепочкой доверия.
    

## Структура URL

```
https://marketplace.example:443/api/v1/products?limit=20#reviews
└─scheme └──────host────────┘port└────path──────┘└query─┘└fragment┘
```

|Часть|Назначение|
|---|---|
|`https`|Схема / протокол доступа|
|`marketplace.example`|Имя хоста|
|`443`|Порт; для HTTPS обычно подразумевается|
|`/api/v1/products`|Путь ресурса|
|`?limit=20`|Query-параметры|
|`#reviews`|Fragment; браузер обычно не отправляет его серверу|

## HTTP-запрос

```
POST /api/v1/orders HTTP/1.1
Host: marketplace.example
Authorization: Bearer <token>
Content-Type: application/json

{"product_id":"42"}
```

|   |   |   |
|---|---|---|
|Часть|Пример|Роль|
|Метод|`POST`|Намерение клиента|
|Target|`/api/v1/orders`|Запрашиваемый ресурс|
|Заголовки|`Content-Type`|Служебная информация|
|Тело|JSON|Передаваемые данные|

## HTTP-ответ

```
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/orders/1001

{"id":"1001","status":"created"}
```

|   |   |
|---|---|
|Часть|Роль|
|Статус-код|Результат обработки|
|Заголовки|Метаданные ответа и инструкции клиенту|
|Тело|Данные или описание ошибки|

## Методы

|   |   |   |
|---|---|---|
|Метод|Типичный смысл|Идемпотентен|
|`GET`|Получить ресурс|Да|
|`POST`|Создать ресурс или запустить действие|Обычно нет|
|`PUT`|Полностью заменить ресурс|Да|
|`PATCH`|Частично изменить ресурс|Зависит от операции|
|`DELETE`|Удалить ресурс|Да по ожидаемому итоговому состоянию|

> [!warning]  
> `GET` не должен изменять состояние. Идемпотентность не означает, что ответ всегда одинаковый; она означает, что повтор запроса не создаёт новых дополнительных изменений после первого успешного выполнения.

## Группы статус-кодов

|   |   |   |
|---|---|---|
|Диапазон|Смысл|Примеры|
|`1xx`|Информационные|`101 Switching Protocols`|
|`2xx`|Успех|`200`, `201`, `204`|
|`3xx`|Перенаправление / cache|`301`, `304`|
|`4xx`|Ошибка запроса клиента|`400`, `401`, `403`, `404`, `409`, `422`, `429`|
|`5xx`|Ошибка сервера или upstream|`500`, `502`, `503`, `504`|

Особенно важно:

```
401 → нет действительной authentication
403 → личность известна, но действие запрещено
404 → ресурс не найден или намеренно скрыт
409 → конфликт с текущим состоянием
429 → превышен rate limit
```

Подробнее: [[03. Authentication и Authorization]].

## Stateless, cookie и session

HTTP сам по себе не требует хранения состояния между запросами. Состояние добавляет приложение:

```
Ответ сервера:  Set-Cookie: session_id=abc123
Следующий запрос: Cookie: session_id=abc123
```

Cookie — механизм браузера. Session — состояние на сервере, связанное с идентификатором из cookie.

Подробнее: [[03. Authentication и Authorization]].

## Путь HTTPS-запроса

```
sequenceDiagram
    participant B as Browser
    participant D as DNS
    participant S as Server
    B->>D: Где marketplace.example?
    D-->>B: IP-адрес
    B->>S: TCP-соединение
    B->>S: TLS handshake
    S-->>B: Сертификат и параметры TLS
    B->>S: Зашифрованный HTTP-запрос
    S-->>B: Зашифрованный HTTP-ответ
```

Упрощённо TLS handshake:

1. Клиент и сервер согласуют безопасные параметры.
    
2. Сервер предъявляет сертификат.
    
3. Клиент проверяет имя хоста, срок действия и цепочку доверия.
    
4. Стороны получают общие ключи сеанса.
    
5. HTTP передаётся в зашифрованном виде.
    

## Что защищает HTTPS

- содержимое запроса и ответа от чтения по пути;
    
- трафик от незаметного изменения;
    
- клиента от подключения к серверу без подходящего сертификата.
    

## Чего HTTPS не защищает

- от SQL injection, XSS, CSRF и ошибок authorization;
    
- от вредоносного кода на самом клиенте или сервере;
    
- от утечки данных в логах;
    
- от слабых паролей;
    
- от неправильно выданного доступа к ресурсу.
    

> [!danger]  
> HTTPS защищает канал, а не бизнес-логику приложения.

## Reverse proxy и заголовки

В production TLS часто завершается на reverse proxy или Ingress Controller:

```
Клиент → HTTPS → reverse proxy → HTTP или HTTPS → приложение
```

Приложению важно доверять forwarding-заголовкам (`Forwarded`, `X-Forwarded-For`, `X-Forwarded-Proto`) только от своего proxy. Иначе внешний клиент сможет подделать информацию об IP или схеме запроса.

## Security-заголовки: ориентир

|   |   |
|---|---|
|Заголовок|Зачем нужен|
|`Strict-Transport-Security`|Требовать HTTPS для домена|
|`Content-Security-Policy`|Ограничить источники исполняемого контента|
|`X-Content-Type-Options: nosniff`|Запретить угадывание типа контента|
|`Referrer-Policy`|Ограничить данные в `Referer`|
|`Permissions-Policy`|Ограничить браузерные возможности|

Заголовки усиливают защиту, но не исправляют небезопасную обработку входных данных.
