

> [!summary] Главная идея  
> Если злоумышленник получил RCE в Pod, настройки Kubernetes должны уменьшить его права, доступ к Kubernetes API, сети и secrets.

## Четыре уровня

```
flowchart TD
    S["securityContext — процесс"] --> A["ServiceAccount — идентичность"]
    A --> R["RBAC — права Kubernetes API"]
    R --> N["NetworkPolicy — сетевые связи"]
```

## `securityContext`

`securityContext` задаёт права и ограничения Pod или контейнера.

```
spec:
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    seccompProfile:
      type: RuntimeDefault

  containers:
    - name: api
      image: marketplace-api:1.0.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop:
            - ALL
```

|Настройка|Результат|
|---|---|
|`runAsNonRoot: true`|Запрещает запуск процесса как UID `0`|
|`runAsUser: 10001`|Фиксирует непривилегированный UID|
|`allowPrivilegeEscalation: false`|Не даёт процессу получить новые привилегии|
|`readOnlyRootFilesystem: true`|Запрещает запись в filesystem image|
|`capabilities.drop: ALL`|Удаляет дополнительные Linux capabilities|
|`seccompProfile: RuntimeDefault`|Применяет стандартное ограничение syscalls runtime|

Если приложение пишет временные файлы, выделяем отдельный volume:

```
volumeMounts:
  - name: tmp
    mountPath: /tmp

volumes:
  - name: tmp
    emptyDir: {}
```

> [!note]  
> `runAsNonRoot` запрещает начать работу от root. `allowPrivilegeEscalation: false` запрещает уже запущенному процессу повысить привилегии. Эти меры решают разные задачи.

## ServiceAccount

ServiceAccount — не-человеческая идентичность workload перед Kubernetes.

```
ServiceAccount → удостоверение личности Pod
RBAC           → права этой личности
Token          → доказательство личности для Kubernetes API
```

Пример:

```
apiVersion: v1
kind: ServiceAccount
metadata:
  name: marketplace-api
```

Подключение:

```
spec:
  serviceAccountName: marketplace-api
```

Обычному FastAPI чаще всего не нужно обращаться к Kubernetes API. Тогда токен лучше не монтировать:

```
automountServiceAccountToken: false
```

ServiceAccount не заменяет PostgreSQL user, Kafka credentials или пользователя Marketplace.

## RBAC

RBAC отвечает на три вопроса:

```
Кто? → Что может сделать? → Над каким объектом Kubernetes?
```

Основные объекты:

|   |   |
|---|---|
|Объект|Назначение|
|Role|Права внутри одного Namespace|
|ClusterRole|Права cluster-wide или переиспользуемый набор правил|
|RoleBinding|Назначает Role / ClusterRole внутри Namespace|
|ClusterRoleBinding|Назначает ClusterRole на уровне всего кластера|

Пример ограниченной Role для deployer:

```
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: marketplace-deployer
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "patch", "update"]
```

Читается так:

```
resources → над чем: deployments
verbs     → что можно: get, list, patch, update
```

Опасно без необходимости:

```
resources: ["*"]
verbs: ["*"]
```

Это означает широкие действия над всеми подходящими ресурсами. Особенно опасны `cluster-admin`, чтение всех Secrets и право создавать привилегированные workload.

## NetworkPolicy

NetworkPolicy — сетевой allowlist для Pod на уровнях IP и портов.

Начальная политика «запретить всё»:

```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

Построчно:

```
podSelector: {} → выбрать все Pod в этом Namespace
Ingress         → контролировать входящие соединения к Pod
Egress          → контролировать исходящие соединения из Pod
нет allow rules → выбранный трафик запрещён
```

После этого создаются отдельные разрешения:

```
Ingress Controller → API:8000
API → PostgreSQL:5432
API → Redis:6379
API → Kafka:9092
API → cluster DNS
Worker → Kafka:9092
```

> [!warning]  
> Egress deny блокирует DNS, поэтому DNS нужно разрешить явно. NetworkPolicy работает только с CNI-плагином, который умеет её применять.

## Namespace

Namespace помогает разделить:

- RBAC;
    
- NetworkPolicy;
    
- Secrets и ConfigMaps;
    
- quotas и policies;
    
- команды и окружения.
    

```
marketplace
observability
ingress-system
database
```

Но Namespace сам по себе не является security boundary. Без RBAC и NetworkPolicy Pod из разных областей всё ещё могут иметь лишний доступ.

## Secrets

Kubernetes Secret предназначен для конфиденциальных значений, но по умолчанию данные могут храниться в `etcd` без encryption at rest.

Минимум:

- включить encryption at rest;
    
- ограничить чтение через RBAC;
    
- не выдавать лишнее право создавать Pod в Namespace с secrets;
    
- монтировать только нужные ключи;
    
- не выводить secrets в manifests, shell history и логи;
    
- для серьёзного production рассмотреть внешний secret manager.
    

## Pod Security Standards

|   |   |
|---|---|
|Уровень|Смысл|
|`privileged`|Почти без ограничений|
|`baseline`|Запрещает известные опасные настройки|
|`restricted`|Строгий security-профиль для workload|

Для приложения цель — совместимость с `restricted`. Удобный путь: сначала warning/audit, исправление manifests, затем enforce.

## Как меняется blast radius RCE

Без hardening:

```
RCE → root в контейнере
→ token Kubernetes API
→ чтение Secrets
→ соединение со всеми Pod
→ создание привилегированного workload
```

С hardening:

```
RCE → non-root
→ read-only filesystem
→ нет privilege escalation
→ нет Kubernetes API token
→ RBAC не даёт лишних действий
→ NetworkPolicy оставляет только необходимые соединения
```

RCE остаётся серьёзной уязвимостью, но зона поражения уменьшается.

## Практический порядок внедрения

1. Запустить приложение с `runAsNonRoot`.
    
2. Удалить capabilities и запретить privilege escalation.
    
3. Сделать root filesystem read-only и выделить writable paths.
    
4. Отключить automount ServiceAccount token, если API не нужен.
    
5. Проверить права через `kubectl auth can-i`.
    
6. Включить default deny в тестовом Namespace.
    
7. По одному разрешить реальные network flows и DNS.
    
8. Проверить совместимость с Pod Security `restricted`.
    

## Минимальный checklist

- Контейнер работает non-root.
    
- Root filesystem read-only.
    
- Privilege escalation выключен.
    
- Все ненужные capabilities удалены.
    
- Используется `RuntimeDefault` seccomp.
    
- Kubernetes API token не монтируется без необходимости.
    
- RBAC следует least privilege.
    
- NetworkPolicy явно разрешает только нужные связи.
    
- Secrets защищены encryption at rest и RBAC.
    
- Namespace имеет подходящую Pod Security policy.
