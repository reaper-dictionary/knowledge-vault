# 1. Краткие определения — выучить

## IP-адрес

> **IP-адрес** — логический адрес сетевого интерфейса, по которому пакеты доставляются до нужного устройства или контейнера.

## DNS

> **DNS** — распределённая система, которая преобразует доменные имена и имена сервисов в IP-адреса.

## TCP

> **TCP** — транспортный протокол, который устанавливает соединение и обеспечивает надёжную передачу данных в правильном порядке.

## HTTP

> **HTTP** — прикладной протокол, который определяет структуру и смысл запросов и ответов: методы, заголовки, тело и статус-коды.

## Порт

> **Порт** — число от `0` до `65535`, по которому операционная система направляет сетевой трафик нужному сервису.

## `127.0.0.1` и `localhost`

> `127.0.0.1` — IPv4-адрес loopback: он всегда указывает на ту машину или контейнер, внутри которого выполняется обращение. `localhost` обычно преобразуется в loopback-адрес.

## `0.0.0.0` и `[::]`

> `0.0.0.0` **при привязке** означает прослушивание порта на всех IPv4-интерфейсах, а `[::]` — на всех IPv6-интерфейсах текущей машины или контейнера.

## Docker DNS

> **Docker DNS** преобразует имя Compose-сервиса, например `postgres`, во внутренний IP соответствующего контейнера.

## Порт хоста и порт контейнера

> Запись `5433:5432` означает: **порт хоста** `5433` **перенаправляется на порт контейнера** `5432`.

## API Gateway и сетевой gateway

> **API Gateway** принимает прикладные запросы и передаёт их внутренним сервисам. **Сетевой gateway** передаёт IP-пакеты между разными сетями.

## Минимальная поверхность атаки

> **Минимальная поверхность атаки** — принцип, по которому наружу публикуются только необходимые сервисы и порты.

## Главные формулы

```
IP → нужное устройство или контейнер
Порт → нужный сервис внутри него
```

```
URL → DNS → IP → TCP → TLS при HTTPS → HTTP
```

```
Имя сервиса → Docker DNS → IP контейнера → порт → TCP-соединение
```

# 2. Подробные объяснения — понять

## 2.1. IP-адрес и порт

IP-адрес и порт решают разные задачи:

- IP-адрес помогает доставить пакет до нужного сетевого интерфейса;
    
- порт помогает операционной системе передать трафик нужному сервису;
    
- вместе они образуют адрес сетевой точки подключения, например `203.0.113.10:443`.
    

```
203.0.113.10:22    → SSH
203.0.113.10:443   → reverse proxy
203.0.113.10:8000  → FastAPI
203.0.113.10:5432  → PostgreSQL
```

IP не выбирает конкретное приложение. На одном IP могут одновременно работать FastAPI, PostgreSQL, SSH и другие сервисы, если они слушают разные порты.

## 2.2. DNS

Людям удобнее запоминать имена, а сети работают с IP-адресами. DNS выполняет преобразование:

```
marketplace.example → 203.0.113.10
```

DNS не отправляет HTTP-запрос и не устанавливает TCP-соединение. Он возвращает IP-адрес, после чего клиент самостоятельно подключается к нужному IP и порту.

В Docker роль доменного имени может выполнять имя Compose-сервиса:

```
postgres → 172.19.0.4
room_service → 172.19.0.6
```

## 2.3. TCP и HTTP

TCP и HTTP находятся на разных уровнях:

|Протокол|За что отвечает|
|---|---|
|TCP|Соединение, порядок байтов, обнаружение потерь и повторная передача|
|HTTP|Методы, URL, заголовки, тело запроса, ответ и статус-коды|

Для TCP HTTP-запрос — просто последовательность байтов. TCP надёжно передаёт эти байты, но не понимает, что означают `GET`, `POST` или `404`.

## 2.4. Что происходит после ввода URL

Например, для `https://marketplace.example/products` браузер:

1. Разбирает URL: схему, домен, порт и путь.
    
2. Через DNS получает IP домена.
    
3. Устанавливает TCP-соединение с нужным IP и портом.
    
4. Для HTTPS выполняет TLS handshake.
    
5. Передаёт HTTP-запрос внутри защищённого соединения.
    
6. Получает HTTP-ответ.
    

```
Разбор URL → DNS → TCP → TLS → HTTP-запрос → HTTP-ответ
```

## 2.5. `127.0.0.1`, `0.0.0.0` и `[::]`

### `127.0.0.1`

`127.0.0.1` — IPv4 loopback. При подключении он означает: «обратиться к этой же машине или к этому же контейнеру».

```
127.0.0.1:8000 → сервис на текущей машине или в текущем контейнере
```

Если процесс привязан только к `127.0.0.1`, подключения через другие сетевые интерфейсы он не принимает.

### `0.0.0.0`

`0.0.0.0` используется для привязки сервера и означает все IPv4-интерфейсы текущего сетевого пространства.

```
0.0.0.0:8000 → слушать порт 8000 на всех IPv4-интерфейсах
```

Привязка к `0.0.0.0` сама по себе не открывает сервис в интернет. Ещё нужны маршрут или NAT, публикация Docker-порта и разрешение firewall.

### `[::]`

`[::]` выполняет ту же роль для IPv6. Поэтому `ss` на хосте может показывать две строки для одного опубликованного порта:

```
0.0.0.0:8000 → все IPv4-интерфейсы хоста
[::]:8000     → все IPv6-интерфейсы хоста
```

Обе строки относятся к хосту, если команда `ss` запущена на хосте. Они не означают «контейнер» и «компьютер».

## 2.6. `localhost` внутри контейнера

У каждого контейнера обычно отдельное сетевое пространство. Поэтому `localhost` внутри Gateway указывает на сам контейнер Gateway, а не на ноутбук и не на Room Service.

Неправильно:

```
localhost:50051
```

Правильно:

```
room_service:50051
```

Результат нашей проверки:

```
room_service:50051 = 0   → TCP-соединение установлено
localhost:50051 = 111    → Connection refused
```

## 2.7. Как контейнеры находят друг друга

Docker Compose создаёт общую сеть и предоставляет встроенный DNS. Каждый контейнер является отдельным сетевым узлом, поэтому получает собственный внутренний IP:

```
kafka        → 172.19.0.2
postgres     → 172.19.0.4
redis        → 172.19.0.5
room_service → 172.19.0.6
```

Адреса разные, потому что два узла в одной сети не могут использовать один IP. После пересоздания контейнеров эти IP могут измениться, поэтому в конфигурации используют стабильные имена сервисов:

```
room_service:50051
postgres:5432
redis:6379
kafka:29092
```

Например, подключение Gateway к Room Service происходит так:

```
room_service → Docker DNS → 172.19.0.6 → порт 50051 → TCP-соединение
```

## 2.8. API Gateway и сетевой gateway

Наш `gateway` — это прикладной сервис проекта. Он принимает HTTP/WebSocket-запросы пользователей и вызывает внутренние сервисы, например Room Service через gRPC.

```
Пользователь → Gateway Service → gRPC → Room Service
```

Сетевой gateway — это шлюз или маршрутизатор, который передаёт IP-пакеты из одной сети в другую.

В команде:

```
docker compose exec gateway python -c "..."
```

`gateway` — имя нашего Compose-сервиса. Docker запускает Python-код внутри контейнера Gateway. К сетевому gateway эта команда не обращается.

## 2.9. Порты хоста и контейнера

Запись Compose:

```
ports:
  - "5433:5432"
```

означает:

```
хост:5433 → Docker-проброс → контейнер PostgreSQL:5432
```

Поэтому используются разные адреса:

```
DBeaver на ноутбуке → localhost:5433
Gateway в Docker    → postgres:5432
```

Ошибочные варианты:

```
Gateway → postgres:5433    ✗
Gateway → localhost:5433   ✗
```

`postgres:5433` неверен, потому что PostgreSQL внутри контейнера слушает `5432`. `localhost:5433` внутри Gateway неверен, потому что loopback указывает на сам Gateway.

## 2.10. Порты Realtime Rooms Lab

|   |   |   |
|---|---|---|
|Сервис|С хоста|Внутри Docker-сети|
|Gateway|`localhost:8000`|`gateway:8000`|
|Room Service|`localhost:50051`|`room_service:50051`|
|PostgreSQL|`localhost:5433`|`postgres:5432`|
|Redis|`localhost:6379`|`redis:6379`|
|Kafka|`localhost:9092`|`kafka:29092`|

В production внутренние сервисы необязательно публиковать на хост. Для разработки публикация удобна, например чтобы подключить DBeaver к PostgreSQL.

## 2.11. Что проверяют диагностические команды

### `ss -ltn`

```
ss -ltn
```

Показывает TCP-порты в состоянии `LISTEN` в том сетевом пространстве, где выполнена команда. Это доказывает, что кто-то принимает TCP-соединения на порту, но не гарантирует исправность приложения.

### `connect_ex()`

```
s.connect_ex(("postgres", 5432))
```

- `0` — TCP-соединение установлено;
    
- ненулевой код, например `111`, — соединение не установлено.
    

Эта проверка не доказывает, что PostgreSQL или gRPC корректно работают по своему протоколу.

### `pg_isready`

```
pg_isready -h 127.0.0.1 -p 5432
```

`pg_isready` обращается по протоколу PostgreSQL и проверяет, принимает ли сервер подключения. Он не гарантирует, что конкретные логин, пароль и база данных подходят.

```
connect_ex() == 0 → доступен TCP-порт
pg_isready        → отвечает PostgreSQL
реальный запрос   → подходят доступы и работает нужная база
```

## 2.12. Почему внутренние сервисы не публикуют в интернет

В production наружу обычно публикуют только reverse proxy или Gateway на `443`. PostgreSQL, Redis, Kafka и внутренние gRPC-сервисы оставляют во внутренней сети.

```
Пользователь → HTTPS/WSS → Reverse proxy/Gateway
Gateway → gRPC → Room Service
Room Service → PostgreSQL
Сервисы → Redis/Kafka
```

Публикация внутренних сервисов увеличивает риск:

- подбора логинов и паролей;
    
- эксплуатации уязвимостей;
    
- перегрузки соединениями;
    
- обхода авторизации и бизнес-правил API.
    

Это и есть применение принципа минимальной поверхности атаки.

# 3. Связный ответ для собеседования

> После ввода URL браузер получает IP домена через DNS и устанавливает TCP-соединение с нужным IP и портом. IP определяет сетевой интерфейс, порт — сервис, а TCP обеспечивает надёжную упорядоченную передачу данных. Для HTTPS выполняется TLS handshake, после чего передаются HTTP-запросы и ответы.
> 
> В Docker Compose контейнеры находят друг друга через встроенный DNS по имени сервиса, например `room_service:50051`. `localhost` внутри контейнера указывает на этот же контейнер. Запись `5433:5432` означает перенаправление порта `5433` хоста на порт `5432` контейнера, поэтому DBeaver использует `localhost:5433`, а соседние контейнеры — `postgres:5432`.
> 
> В production наружу следует публиковать только необходимые точки входа, обычно HTTPS/WSS на порту `443`, а базы данных, брокеры и внутренние gRPC-сервисы оставлять во внутренней сети.

Docker Compose создаёт общую сеть и предоставляет встроенный DNS. Каждый контейнер является отдельным сетевым узлом, поэтому получает собственный внутренний IP:

```
kafka        → 172.19.0.2
postgres     → 172.19.0.4
redis        → 172.19.0.5
room_service → 172.19.0.6
```

Адреса разные, потому что два узла в одной сети не могут использовать один IP. После пересоздания контейнеров эти IP могут измениться, поэтому в конфигурации используют стабильные имена сервисов:

```
room_service:50051
postgres:5432
redis:6379
kafka:29092
```

Например, подключение Gateway к Room Service происходит так:

```
room_service → Docker DNS → 172.19.0.6 → порт 50051 → TCP-соединение
```

## 2.8. API Gateway и сетевой gateway

Наш `gateway` — это прикладной сервис проекта. Он принимает HTTP/WebSocket-запросы пользователей и вызывает внутренние сервисы, например Room Service через gRPC.

```
Пользователь → Gateway Service → gRPC → Room Service
```

Сетевой gateway — это шлюз или маршрутизатор, который передаёт IP-пакеты из одной сети в другую.

В команде:

```
docker compose exec gateway python -c "..."
```

`gateway` — имя нашего Compose-сервиса. Docker запускает Python-код внутри контейнера Gateway. К сетевому gateway эта команда не обращается.

## 2.9. Порты хоста и контейнера

Запись Compose:

```
ports:
  - "5433:5432"
```

означает:

```
хост:5433 → Docker-проброс → контейнер PostgreSQL:5432
```

Поэтому используются разные адреса:

```
DBeaver на ноутбуке → localhost:5433
Gateway в Docker    → postgres:5432
```

Ошибочные варианты:

```
Gateway → postgres:5433    ✗
Gateway → localhost:5433   ✗
```

`postgres:5433` неверен, потому что PostgreSQL внутри контейнера слушает `5432`. `localhost:5433` внутри Gateway неверен, потому что loopback указывает на сам Gateway.

## 2.11. Что проверяют диагностические команды

### `ss -ltn`

```
ss -ltn
```

Показывает TCP-порты в состоянии `LISTEN` в том сетевом пространстве, где выполнена команда. Это доказывает, что кто-то принимает TCP-соединения на порту, но не гарантирует исправность приложения.

### `connect_ex()`

```
s.connect_ex(("postgres", 5432))
```

- `0` — TCP-соединение установлено;
    
- ненулевой код, например `111`, — соединение не установлено.
    

Эта проверка не доказывает, что PostgreSQL или gRPC корректно работают по своему протоколу.

### `pg_isready`

```
pg_isready -h 127.0.0.1 -p 5432
```

`pg_isready` обращается по протоколу PostgreSQL и проверяет, принимает ли сервер подключения. Он не гарантирует, что конкретные логин, пароль и база данных подходят.

```
connect_ex() == 0 → доступен TCP-порт
pg_isready        → отвечает PostgreSQL
реальный запрос   → подходят доступы и работает нужная база
```

## 2.12. Почему внутренние сервисы не публикуют в интернет

В production наружу обычно публикуют только reverse proxy или Gateway на `443`. PostgreSQL, Redis, Kafka и внутренние gRPC-сервисы оставляют во внутренней сети.

```
Пользователь → HTTPS/WSS → Reverse proxy/Gateway
Gateway → gRPC → Room Service
Room Service → PostgreSQL
Сервисы → Redis/Kafka
```

Публикация внутренних сервисов увеличивает риск:

- подбора логинов и паролей;
    
- эксплуатации уязвимостей;
    
- перегрузки соединениями;
    
- обхода авторизации и бизнес-правил API.
    

Это и есть применение принципа минимальной поверхности атаки.

# 3. Связный ответ для собеседования

> После ввода URL браузер получает IP домена через DNS и устанавливает TCP-соединение с нужным IP и портом. IP определяет сетевой интерфейс, порт — сервис, а TCP обеспечивает надёжную упорядоченную передачу данных. Для HTTPS выполняется TLS handshake, после чего передаются HTTP-запросы и ответы.
> 
> В Docker Compose контейнеры находят друг друга через встроенный DNS по имени сервиса, например `room_service:50051`. `localhost` внутри контейнера указывает на этот же контейнер. Запись `5433:5432` означает перенаправление порта `5433` хоста на порт `5432` контейнера, поэтому DBeaver использует `localhost:5433`, а соседние контейнеры — `postgres:5432`.
> 
> В production наружу следует публиковать только необходимые точки входа, обычно HTTPS/WSS на порту `443`, а базы данных, брокеры и внутренние gRPC-сервисы оставлять во внутренней сети.
