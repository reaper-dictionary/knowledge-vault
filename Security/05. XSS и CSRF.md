
> [!summary] Разница одной строкой  
> **XSS** запускает код злоумышленника внутри origin нашего сайта.  
> **CSRF** заставляет браузер отправить нежелательный authenticated-запрос с другого сайта.

## XSS

**Cross-Site Scripting** возникает, когда недоверенные данные попадают в исполняемый контекст страницы.

Пример stored XSS:

```
Злоумышленник сохраняет комментарий с опасной разметкой
→ Marketplace отдаёт его без безопасного вывода
→ браузер жертвы выполняет чужой JavaScript в origin Marketplace
```

Возможности вредоносного скрипта:

- читать и изменять DOM;
    
- читать токены из `localStorage`;
    
- отправлять запросы от имени пользователя;
    
- читать cookie без `HttpOnly`;
    
- подменять форму и похищать ввод.
    

### Основные виды XSS

|Вид|Где находится payload|
|---|---|
|Stored|Сохранён на сервере: комментарий, профиль, описание|
|Reflected|Возвращается прямо из текущего запроса|
|DOM-based|Небезопасно обрабатывается frontend-кодом в браузере|

### Защита от XSS

- контекстное экранирование вывода;
    
- безопасные DOM API, например `textContent` вместо `innerHTML`;
    
- отсутствие `dangerouslySetInnerHTML` без необходимости;
    
- проверенная sanitization-библиотека, если HTML действительно разрешён;
    
- Content Security Policy как дополнительный слой;
    
- `HttpOnly` для чувствительных cookie;
    
- запрет `eval()` и подобных динамических исполнений.
    

> [!warning]  
> Валидация входа полезна, но основной XSS-контроль — безопасный вывод в конкретный HTML, attribute, URL, CSS или JavaScript-контекст.

## CSRF

**Cross-Site Request Forgery** использует то, что браузер автоматически прикладывает подходящие cookie.

```
Пользователь вошёл в Marketplace
→ открывает сайт злоумышленника
→ тот инициирует запрос в Marketplace
→ браузер автоматически добавляет session cookie
→ backend может принять запрос за действие пользователя
```

Атакующему часто не нужно читать ответ — достаточно выполнить изменение.

### Когда CSRF особенно актуален

- authentication основана на автоматически отправляемой cookie;
    
- endpoint изменяет состояние;
    
- сервер не проверяет происхождение запроса;
    
- cookie разрешено отправляться в нужном cross-site контексте.
    

### Защита от CSRF

- `SameSite=Lax` или `SameSite=Strict`, если сценарий позволяет;
    
- synchronizer token или другой корректный CSRF-токен;
    
- проверка `Origin`, а при необходимости `Referer`;
    
- custom header для API, который frontend добавляет явно;
    
- запрет изменения состояния через `GET`;
    
- повторная authentication для критических действий.
    

> [!note]  
> `SameSite` — сильный слой, но решение зависит от браузерных сценариев, subdomain и интеграций. Для чувствительных операций не стоит полагаться на один контроль.

## Сравнение

|   |   |   |
|---|---|---|
|Вопрос|XSS|CSRF|
|Что делает атакующий|Выполняет код внутри нашего origin|Инициирует запрос с другого origin|
|Главная причина|Небезопасный вывод данных|Автоматическая отправка credentials|
|Может читать ответ|Обычно да|Обычно нет|
|Основная защита|Контекстное экранирование и безопасные API|CSRF token, `SameSite`, проверка origin|
|Помогает ли `HttpOnly`|Не даёт прочитать cookie|Не мешает браузеру отправить cookie|

## Где хранить токены

```
Access token в localStorage
→ браузер не прикладывает его автоматически
→ классический CSRF сложнее
→ XSS может прочитать и украсть токен
```

```
Session / refresh token в HttpOnly cookie
→ JavaScript не может прочитать значение
→ браузер отправляет cookie автоматически
→ нужна CSRF-защита
```

> [!danger]  
> Нет варианта хранения, который отменяет остальные меры. `HttpOnly` уменьшает часть последствий XSS, но вредоносный скрипт всё ещё может выполнять запросы из открытой страницы.

## Marketplace: пример защиты

Для `POST /api/v1/orders` при cookie-based session:

1. Endpoint не принимает `GET`.
    
2. Session cookie имеет `HttpOnly`, `Secure`, подходящий `SameSite`.
    
3. Frontend отправляет CSRF token или специальный header.
    
4. Backend проверяет `Origin`.
    
5. Backend отдельно выполняет authorization и бизнес-проверки.
    
6. Пользовательский контент выводится безопасно, чтобы XSS не обошёл браузерные меры.
    

## Минимальный checklist

- Нет небезопасной вставки пользовательского HTML.
    
- Вывод экранируется под конкретный контекст.
    
- CSP настроена как дополнительный слой.
    
- Чувствительные cookie имеют `HttpOnly` и `Secure`.
    
- State-changing endpoints не используют `GET`.
    
- Cookie-based authentication имеет CSRF-защиту.
    
- Проверяются origin и authorization.
    
- Защита проверена реальными запросами через browser devtools или Burp.
