

> [!summary] Главное различие  
> **Authentication (AuthN)** отвечает: «Кто ты?»  
> **Authorization (AuthZ)** отвечает: «Что тебе разрешено?»

Сначала backend устанавливает личность, затем проверяет право на конкретное действие.

## `401`, `403` и скрытый `404`

|Код|Смысл|
|---|---|
|`401 Unauthorized`|Credentials отсутствуют, недействительны или истекли|
|`403 Forbidden`|Пользователь известен, но действие ему запрещено|
|`404 Not Found`|Ресурс не найден; иногда так скрывают существование чужого ресурса|

> [!note]  
> Название `401 Unauthorized` исторически неудачно: по смыслу это ошибка authentication.

## Проверка доступа к ресурсу

Роли недостаточно. Для `PATCH /products/42` backend проверяет:

1. Действительна ли сессия или access token.
    
2. Существует ли пользователь и активен ли он.
    
3. Разрешено ли действие его роли.
    
4. Принадлежит ли ресурс этому пользователю.
    
5. Разрешает ли действие текущее состояние ресурса.
    

```
product.seller_id == current_user.id
```

```
Authentication → Role → Ownership → Resource state → Action
```

Скрытая кнопка во frontend не является защитой: запрос можно отправить через `curl` или Burp. Решение всегда принимает backend.

## Cookie — транспорт, а не способ входа

Cookie — значение, которое браузер хранит и автоматически отправляет подходящему сайту.

```
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Path=/
```

|   |   |
|---|---|
|Атрибут|Роль|
|`HttpOnly`|JavaScript не может прочитать cookie через `document.cookie`|
|`Secure`|Cookie отправляется только по HTTPS|
|`SameSite`|Ограничивает автоматическую отправку в cross-site контексте|
|`Max-Age` / `Expires`|Срок жизни|
|`Path` / `Domain`|Область действия|

Cookie может переносить идентификатор server-side session, refresh token или другое значение. Сама cookie не является отдельной схемой authentication.

## Server-side session

После входа сервер создаёт непредсказуемый идентификатор:

```
session_id = случайная секретная строка
```

Состояние хранится на сервере:

```
session_id → user_id, expires_at, metadata
```

Браузеру передаётся только идентификатор:

```
Браузер → Cookie: session_id=abc123
Backend → находит session → получает user_id
```

Плюсы:

- немедленный отзыв;
    
- простой logout;
    
- роли и состояние остаются на сервере.
    

Минус: всем экземплярам backend нужно общее хранилище, например Redis или PostgreSQL.

## JWT

JWT имеет три части:

```
header.payload.signature
```

Пример claims:

```
{
  "sub": "user-id",
  "role": "seller",
  "exp": 1785610000,
  "iss": "marketplace-auth",
  "aud": "marketplace-api"
}
```

> [!warning]  
> JWT обычно подписан, но не зашифрован. Payload можно прочитать без ключа, поэтому в него нельзя помещать пароли, секреты и лишние персональные данные.

Backend проверяет:

- подпись;
    
- ожидаемый алгоритм;
    
- `exp` — срок действия;
    
- `iss` — издателя;
    
- `aud` — получателя;
    
- необходимые claims и состояние пользователя.
    

Простое декодирование без проверки подписи ничего не доказывает.

## Access token и refresh token

Названия описывают назначение, а JWT — формат. Access token может быть JWT, а refresh token — случайной непрозрачной строкой.

```
sequenceDiagram
    participant C as Client
    participant A as Auth service
    C->>A: Логин и пароль
    A-->>C: Access A1 + Refresh R1
    C->>A: R1 на /auth/refresh
    A-->>C: Access A2 + Refresh R2
```

### Access token

- короткий срок жизни;
    
- отправляется обычным API;
    
- даёт доступ только до истечения или отзыва в выбранной схеме.
    

```
Authorization: Bearer <access-token>
```

### Refresh token

- долгий срок жизни;
    
- используется только endpoint обновления;
    
- хранится и передаётся строже;
    
- должен поддерживать отзыв и безопасную ротацию.
    

```
R1 → refresh → A2 + R2
R1 становится недействительным
```

Повторное использование старого `R1` может означать кражу. Тогда сервер отзывает связанную цепочку и требует повторный вход.

|   |   |   |   |
|---|---|---|---|
|Токен|Где используется|Типичный срок|Риск кражи|
|Access|Обычные API-запросы|Минуты|Доступ до истечения|
|Refresh|Только обновление|Дни / недели|Получение новых access tokens|

## Session и JWT — не взаимоисключающие магические решения

|   |   |   |
|---|---|---|
|Вопрос|Server-side session|Самодостаточный JWT access token|
|Где основное состояние|На сервере|В claims токена|
|Немедленный отзыв|Простой|Нужен дополнительный механизм или короткий TTL|
|Масштабирование|Общее session storage|Проверка подписи на каждом сервисе|
|Риск устаревших ролей|Ниже при чтении состояния|Claims живут до истечения токена|

JWT не является автоматически безопаснее session. Выбор зависит от архитектуры и требований к отзыву.

## Минимальный checklist

- Authentication выполняется централизованно и одинаково во всех endpoints.
    
- Authorization проверяется на backend.
    
- Есть проверка ownership и состояния ресурса.
    
- Access token имеет короткий TTL.
    
- Refresh token ротируется и отзывается.
    
- Cookie использует подходящие `HttpOnly`, `Secure`, `SameSite`, `Path`.
    
- Logout действительно инвалидирует server-side состояние или refresh token.
    
- Секреты и чувствительные данные не лежат в JWT payload.
    
- Логи не содержат пароли, session ID и полные токены.
