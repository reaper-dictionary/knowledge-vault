
- **Authentication** — проверка личности: «Кто ты?»
    
- **Authorization** — проверка разрешений: «Что тебе можно?»
    
- Сначала backend выполняет authentication, затем authorization.
    

### Основные статусы

- `401 Unauthorized` — пользователь не аутентифицирован: credentials отсутствуют, недействительны или истекли.
    
- `403 Forbidden` — пользователь аутентифицирован, но у него недостаточно прав.
    
- Иногда вместо `403` возвращают `404`, чтобы не раскрывать существование чужого ресурса.

### Проверка доступа к ресурсу

Одной роли недостаточно. Например, для `PATCH /products/42` backend должен проверить:

1. Есть ли действительная сессия или токен.
    
2. Существует ли пользователь и активен ли он.
    
3. Имеет ли он роль `seller`.
    
4. Принадлежит ли товар этому продавцу.
    
5. Разрешено ли изменение в текущем состоянии товара, например не архивирован ли он.
    

```
product.seller_id == current_user.id
```

Скрытие кнопки во frontend не является защитой: запрос можно отправить напрямую через `curl` или Burp. Окончательное решение всегда принимает backend.

HTTPS тоже не заменяет проверку прав:

- HTTPS защищает данные во время передачи;
    
- authorization определяет, разрешено ли действие.

## Cookie

Cookie — значение, которое браузер хранит и автоматически отправляет подходящему сайту.

```
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax
```

Основные атрибуты:

- `HttpOnly` — JavaScript не может прочитать cookie;
    
- `Secure` — cookie отправляется только по HTTPS;
    
- `SameSite` — ограничивает отправку cookie в межсайтовых запросах;
    
- `Max-Age` или `Expires` — задаёт срок жизни;
    
- `Path` и `Domain` — задают область действия.
    

Cookie — только механизм хранения и передачи значения. Сама по себе cookie не является отдельным способом authentication.

## Server-side session

После успешного входа сервер создаёт случайный непредсказуемый идентификатор сессии:

```
session_id = случайная секретная строка
```

В Redis или PostgreSQL сервер хранит состояние:

```
session_id → user_id, срок жизни, дополнительные данные
```

Браузеру передаётся только идентификатор:

```
Браузер → Cookie: session_id=abc123
Сервер → находит сессию → определяет пользователя
```

Преимущества:

- сессию легко немедленно отозвать;
    
- logout может удалить её на сервере;
    
- роли и чувствительные данные не нужно хранить у клиента.
    

Недостаток: всем экземплярам backend требуется общее хранилище сессий.

## JWT

JWT обычно состоит из трёх частей:

```
header.payload.signature
```

Payload может содержать claims:

```
{
  "sub": "user-id",
  "role": "seller",
  "exp": 1785610000
}
```

JWT обычно **подписан, но не зашифрован**. Payload можно прочитать без секретного ключа, поэтому в него нельзя помещать пароли и другие секреты.

Подпись позволяет обнаружить изменение токена. Backend должен не просто декодировать JWT, а проверить:

- подпись;
    
- разрешённый алгоритм;
    
- `exp` — срок действия;
    
- `iss` — издателя;
    
- `aud` — целевого получателя.
    

Названия `access token` и `refresh token` описывают **назначение**, а JWT — **формат**. Access token часто делают JWT, а refresh token может быть случайной непрозрачной строкой, хеш которой хранится на сервере.

## Access token и refresh token

### Откуда они берутся

Оба токена создаёт auth-сервис после успешной проверки логина и пароля:

```
Пользователь отправляет логин и пароль
                  ↓
Auth-сервис проверяет credentials
                  ↓
Сервер создаёт access token и refresh token
```

`Refresh token` — **не алгоритм** создания access token. Клиент не вычисляет из него новый токен. Он отправляет refresh token специальному endpoint, а сервер проверяет его и сам создаёт новую пару.

### Access token

Access token — короткоживущий пропуск к обычному API:

```
GET /api/v1/profile
Authorization: Bearer <access-token>
```

Обычно он живёт 5–30 минут и отправляется во многие endpoints и сервисы.

### Refresh token

Refresh token — долгоживущий секрет для продления сессии. Он отправляется только на специальный endpoint:

```
POST /auth/refresh
Cookie: refresh_token=...
```

Сервер проверяет refresh token и выдаёт новый access token. При безопасной ротации он также выдаёт новый refresh token и аннулирует старый:

```
R1 → POST /auth/refresh → A2 + R2
R1 становится недействительным
```

Если старый `R1` позже используют повторно, это может означать его кражу. Сервер может отозвать всю связанную цепочку токенов и потребовать повторный вход.

### Зачем нужны оба токена

Если злоумышленник украл действующий refresh token, он действительно может получить новый access token. Разделение токенов не делает украденный refresh безопасным — кража refresh означает серьёзную компрометацию сессии.

Смысл разделения — уменьшить вероятность и последствия кражи:

|Токен|Где используется|Срок жизни|Последствие кражи|
|---|---|---|---|
|Access|Во множестве обычных API-запросов|Минуты|Доступ до истечения токена|
|Refresh|Только на `/auth/refresh`|Дни или недели|Возможность получать новые access tokens|

Access token чаще перемещается по системе и сильнее подвержен случайной утечке. Благодаря короткому сроку жизни ущерб ограничен.

Refresh token используется редко, не передаётся обычным микросервисам, хранится строже, ротируется и может быть отозван сервером. Если использовать refresh token в каждом API-запросе, долгоживущий секрет постоянно перемещался бы по всей системе, и его кража давала бы доступ на недели.

Для браузерного приложения refresh token часто хранят в `HttpOnly + Secure + SameSite` cookie, а его хеш и состояние сессии — в Redis или PostgreSQL.

## XSS

**XSS (Cross-Site Scripting)** — уязвимость, при которой чужой JavaScript выполняется внутри страницы нашего сайта с его правами.

Пример: Marketplace небезопасно отображает сохранённый пользователем комментарий со скриптом. Другой пользователь открывает страницу, и браузер выполняет код злоумышленника как код Marketplace.

Такой скрипт может:

- прочитать access token из `localStorage`;
    
- прочитать или изменить содержимое страницы;
    
- отправлять запросы от имени пользователя;
    
- украсть cookie, если у неё нет `HttpOnly`.
    

`HttpOnly` не устраняет XSS. Он только запрещает JavaScript читать конкретную cookie. Вредоносный код всё ещё может выполнять действия через открытую страницу.

Основные меры защиты:

- экранировать пользовательские данные;
    
- не вставлять непроверенный HTML;
    
- без необходимости не использовать `dangerouslySetInnerHTML`;
    
- применять Content Security Policy;
    
- хранить чувствительные cookie с `HttpOnly`.

## CSRF

**CSRF (Cross-Site Request Forgery)** — атака, при которой чужой сайт заставляет браузер пользователя отправить запрос на наш сайт, а браузер автоматически прикладывает подходящую cookie.

Пример:

```
Пользователь уже вошёл в Marketplace
                  ↓
Открывает сайт злоумышленника
                  ↓
Чужой сайт отправляет запрос в Marketplace
                  ↓
Браузер автоматически добавляет session cookie
                  ↓
Marketplace может принять запрос за действие пользователя
```

Злоумышленнику необязательно читать ответ — иногда достаточно, чтобы изменение выполнилось.

Основные меры защиты:

- `SameSite=Lax` или `SameSite=Strict`;
    
- отдельный CSRF-токен;
    
- проверка заголовков `Origin` и `Referer`;
    
- не изменять состояние через `GET`;
    
- повторно подтверждать личность для критических операций.

## Разница между XSS и CSRF

|   |   |   |
|---|---|---|
||XSS|CSRF|
|Что делает злоумышленник|Запускает чужой JavaScript внутри нашего сайта|Заставляет браузер отправить запрос с чужого сайта|
|Почему возможна атака|Сайт небезопасно обрабатывает данные или HTML|Браузер автоматически отправляет cookie|
|Основной риск хранения|Токен в `localStorage` можно прочитать при XSS|Cookie нельзя обязательно прочитать, но можно использовать автоматически|

Коротко:

```
localStorage + access token
→ меньше риска классического CSRF
→ токен можно украсть при XSS

HttpOnly cookie
→ JavaScript не может прочитать токен
→ всё равно нужна защита от CSRF
```

Защищаться нужно одновременно от обеих атак.

## Главное для запоминания

1. Authentication отвечает «кто ты?», authorization — «что тебе можно?».
    
2. `401` означает отсутствие действительной authentication, `403` — недостаток прав.
    
3. Cookie — механизм передачи значения, session — серверное состояние, JWT — формат подписанного токена.
    
4. JWT обычно можно прочитать, но нельзя незаметно изменить без действительной подписи.
    
5. Access и refresh создаёт сервер; refresh не является алгоритмом.
    
6. Access живёт недолго и используется в обычном API.
    
7. Refresh живёт дольше, используется только для продления сессии и защищается строже.
    
8. Кража refresh token позволяет получить access token, поэтому нужны ротация, отзыв и обнаружение повторного использования.
    
9. XSS запускает чужой JavaScript внутри сайта.
    
10. CSRF заставляет браузер отправить запрос с автоматически приложенной cookie.
    
11. `HttpOnly` уменьшает последствия XSS, но не устраняет XSS и не заменяет защиту от CSRF.
    
12. JWT не является автоматически безопаснее server-side session.
