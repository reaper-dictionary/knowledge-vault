

> [!summary] Главная идея  
> Контейнер — не отдельная виртуальная машина. Он использует ядро хоста, поэтому взломанное приложение нужно ограничить на уровне пользователя, capabilities, файловой системы, сети, ресурсов и доступа к Docker daemon.

## Модель риска

```
Уязвимость приложения → выполнение кода в контейнере → попытка выйти к хосту
```

Контейнеризация не исправляет RCE. Она должна уменьшить возможности атакующего после RCE.

## Выучить

- запускать приложение не от `root`;
    
- не использовать `privileged: true`;
    
- не монтировать `docker.sock` без крайней необходимости;
    
- не монтировать весь хост `/:/host`;
    
- удалить ненужные Linux capabilities;
    
- запретить privilege escalation;
    
- сделать root filesystem read-only;
    
- публиковать только необходимые порты;
    
- задавать CPU, RAM и PID limits;
    
- не помещать secrets в image и Git.
    

## Почему `root` внутри контейнера опасен

Root контейнера не всегда равен root хоста, но у него больше возможностей внутри namespaces и больше шансов использовать ошибочную конфигурацию или уязвимость ядра/runtime.

В Dockerfile создаём отдельного пользователя:

```
RUN addgroup --system --gid 10001 app \
    && adduser --system --uid 10001 --ingroup app app

USER 10001:10001
```

Приложение должно иметь права только на нужные каталоги.

## Опасные настройки

|Настройка|Риск|
|---|---|
|`privileged: true`|Почти снимает изоляцию и выдаёт широкие возможности контейнеру|
|`/:/host`|Открывает файловую систему хоста|
|`/var/run/docker.sock:/var/run/docker.sock`|Позволяет управлять Docker daemon и фактически хостом|
|`network_mode: host`|Контейнер разделяет сетевое пространство хоста|
|`pid: host`|Видит процессы хоста|
|`cap_add: [ALL]`|Возвращает опасные Linux capabilities|
|`8000:8000`|Публикует API на всех интерфейсах хоста|

> [!danger] Docker socket  
> Процесс с доступом к `docker.sock` может создать привилегированный контейнер, подключить файловую систему хоста и получить над ней контроль. Членство в группе `docker` также даёт возможности уровня root на обычной rootful-установке.

## Capabilities и privilege escalation

Linux capabilities делят полномочия root на отдельные возможности. Приложению FastAPI обычно не нужны дополнительные capabilities.

```
cap_drop:
  - ALL
security_opt:
  - no-new-privileges:true
```

Если конкретная capability действительно нужна, добавляется только она после проверки, а не `ALL`.

## Read-only filesystem

```
read_only: true
tmpfs:
  - /tmp:size=64m,noexec,nosuid,nodev
```

Код и зависимости нельзя изменять во время работы. Для временных файлов выделяется отдельный `tmpfs` или volume с минимальными правами.

Это усложняет закрепление вредоносного файла, но не предотвращает выполнение команд в памяти.

## Ресурсные ограничения

```
cpus: 1.0
mem_limit: 512m
pids_limit: 200
```

Лимиты уменьшают последствия:

- утечки памяти;
    
- fork bomb;
    
- бесконечного цикла;
    
- ситуации, когда один контейнер забирает ресурсы всего хоста.
    

Лимиты не заменяют rate limit и защиту приложения от DoS.

## Порты и сети

Для локальной разработки:

```
ports:
  - "127.0.0.1:8000:8000"
```

Приложение внутри контейнера слушает:

```
0.0.0.0:8000
```

Docker снаружи ограничивает публикацию loopback-интерфейсом хоста. В production наружу обычно открыт reverse proxy на `80/443`, а API, PostgreSQL, Redis и Kafka остаются во внутренних сетях.

Разделяй сети по необходимости:

```
public network:  reverse proxy ↔ API
private network: API ↔ PostgreSQL / Redis / Kafka
```

## Secrets и build

Нельзя копировать `.env` в image:

```
COPY . .
```

если build context содержит secrets. Они могут остаться в слоях, cache, registry и истории сборки даже после удаления в следующем слое.

Минимум:

- `.dockerignore` исключает `.env`, ключи, `.git`, tests/cache при необходимости;
    
- runtime secrets передаются отдельно от image;
    
- build-time secrets передаются через механизм BuildKit secrets;
    
- секреты не выводятся в build logs;
    
- production image не содержит dev-инструменты без необходимости.
    

## Образ и supply chain

- использовать минимальный и поддерживаемый base image;
    
- фиксировать версию, а для строгой воспроизводимости — digest;
    
- регулярно пересобирать image с обновлённой базой;
    
- сканировать зависимости и image на известные уязвимости;
    
- использовать multi-stage build;
    
- не запускать случайные непроверенные images и Dockerfiles;
    
- хранить SBOM и provenance, если проект переходит к production-процессу.
    

> [!note]  
> Маленький image не автоматически безопасен, но меньшее количество пакетов обычно уменьшает поверхность атаки и число потенциальных CVE.

## Пример ограниченного Compose-сервиса

```
services:
  api:
    image: marketplace-api:1.0.0
    user: "10001:10001"
    init: true
    read_only: true
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    tmpfs:
      - /tmp:size=64m,noexec,nosuid,nodev
    ports:
      - "127.0.0.1:8000:8000"
    cpus: 1.0
    mem_limit: 512m
    pids_limit: 200
```

Эта конфигурация требует, чтобы image и приложение действительно поддерживали non-root и read-only режим.

## Проверка hardening

```
docker inspect marketplace-api
docker exec marketplace-api id
docker exec marketplace-api sh -c 'touch /should-fail'
docker stats
ss -ltn
```

Проверяем:

- UID не равен `0`;
    
- запись в root filesystem завершается ошибкой;
    
- published ports совпадают с ожиданиями;
    
- отсутствуют опасные mounts и capabilities;
    
- limits применены;
    
- приложение остаётся работоспособным.
    

## Минимальный checklist

- Image запускается от non-root пользователя.
    
- `privileged` отсутствует.
    
- `docker.sock`, host root, host PID и host network не подключены.
    
- Все capabilities удалены или явно обоснованы.
    
- Включён `no-new-privileges`.
    
- Root filesystem read-only, writable paths выделены отдельно.
    
- CPU, RAM и PID ограничены.
    
- Порты опубликованы только там, где нужны.
    
- Secrets отсутствуют в image, layers, Git и логах.
    
- Base image обновляется и сканируется.
