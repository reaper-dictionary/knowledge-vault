
## Термины

**NAT** — изменение IP-адреса в пакете.

**PAT** — изменение IP-адреса вместе с портом.

**Port publishing** — связь порта хоста с портом контейнера:

```yaml
ports:
  - "3000:80"
```

```text
хост:3000 → frontend:80
```

**veth pair** — пара виртуальных интерфейсов, связывающая network namespace контейнера с хостом.

**Docker bridge** — виртуальный коммутатор, соединяющий контейнеры одной Docker-сети.

**Reverse proxy** — сервер, который принимает запрос клиента и создаёт собственный запрос к backend.

**TLS termination** — завершение TLS-соединения на reverse proxy.

## NAT и публикация портов

### Исходящее соединение

Контейнер `app` имеет внутренний адрес:

```text
172.20.0.5
```

При выходе во внешнюю сеть Docker заменяет исходный адрес:

```text
172.20.0.5:случайный_порт
→
IP_хоста:другой_порт
```

Иначе внешний сервер не смог бы вернуть ответ на внутренний Docker-адрес.

### Входящее соединение

Для frontend:

```yaml
ports:
  - "3000:80"
```

Браузер подключается к:

```text
localhost:3000
```

Docker перенаправляет пакеты к:

```text
frontend:80
```

NAT не создаёт отдельное TCP-соединение. Он только переписывает адреса существующего соединения.

---

## `0.0.0.0` и network namespace

`0.0.0.0` означает:

> слушать все IPv4-интерфейсы текущего network namespace.

Поэтому:

```text
0.0.0.0:80 внутри контейнера
```

не означает, что сервис автоматически доступен на порту `80` хоста.

У хоста и контейнера разные network namespaces.

```text
хост:      localhost:3000
контейнер: 0.0.0.0:80
```

Связь между ними создаёт `ports`.

## veth и Docker bridge

Интерфейс приложения:

```text
контейнер: eth0@if22
```

Его парный интерфейс на хосте:

```text
vethfec385c@if2
```

Хостовой интерфейс подключён к bridge:

```text
br-b32327cd623f
```

Это bridge сети:

```text
coffee_house_default
```

Путь от `app` к `db`:

```text
app eth0
→ veth приложения
→ Docker bridge
→ veth PostgreSQL
→ db eth0
```

Физический Wi-Fi или Ethernet-интерфейс ноутбука здесь не используется.

## Compose DNS

Контейнеры должны обращаться друг к другу по именам сервисов:

```text
db:5432
redis:6379
kafka:9093
app:8000
```

Docker DNS получает текущий IP сервиса.

После разрешения имени приложение отдельно создаёт TCP-соединение.

```text
db
→ DNS возвращает 172.20.0.4
→ app подключается к 172.20.0.4:5432
```

IP контейнера может измениться после пересоздания, а имя `db` останется прежним.

## Reverse proxy и отдельные соединения

Запрос:

```text
http://localhost:3000/health
```

создаёт два TCP-соединения.

### Соединение 1

```text
браузер → frontend/Nginx
```

Docker перенаправляет:

```text
localhost:3000 → frontend:80
```

### Соединение 2

Получив HTTP-запрос, Nginx сам подключается к FastAPI:

```text
Nginx → app:8000
```

NAT и firewall не считаются отдельными TCP-участниками.

Полная модель:

```text
TCP №1:
браузер → Nginx

TCP №2:
Nginx → FastAPI
```

## Firewall

Firewall проверяет пакеты и решает:

```text
разрешить
отбросить
отклонить
```

Он не является сервером и не создаёт отдельное соединение.

Если firewall блокирует запрос к frontend:

```text
браузер ✕→ Nginx
```

Nginx не получит HTTP-запрос и не создаст второе соединение с FastAPI.

---

## TLS termination

Текущий Coffee House использует HTTP:

```text
браузер → HTTP → Nginx
Nginx → HTTP → FastAPI
```

В production возможна схема:

```text
браузер → HTTPS → Nginx → HTTP → FastAPI
```

TLS handshake выполняет Nginx.

```text
Соединение №1:
браузер ⇄ Nginx
TCP + TLS + HTTP

Соединение №2:
Nginx ⇄ FastAPI
TCP + HTTP
```

FastAPI не работает с сертификатом, если TLS завершается на Nginx.

---

## Главное для запоминания

```text
NAT не создаёт новое TCP-соединение.

0.0.0.0 действует только внутри текущего network namespace.

ports связывает порт хоста с портом контейнера.

Контейнеры одной сети соединяются через veth и Docker bridge.

Reverse proxy создаёт отдельное соединение с backend.

Firewall проверяет пакеты, но не является участником TCP-соединения.

TLS может завершаться на Nginx, а до FastAPI идти обычный HTTP.
```
