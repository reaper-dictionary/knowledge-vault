# HTTPS и TLS termination в Nginx

> [!info] Как пользоваться заметкой  
> **Учи только раздел «Краткие определения».** Остальные разделы нужны, чтобы понимать TLS termination, назначение сертификата и private key, причины предупреждений браузера и production-схему портов `80/443`.

---

# 1. Краткие определения — выучить

## HTTPS

> **HTTPS** — передача HTTP внутри защищённого TLS-соединения.

## TLS

> **TLS** — криптографический протокол, который шифрует соединение, проверяет целостность данных и позволяет клиенту аутентифицировать сервер по сертификату.

## TLS handshake

> **TLS handshake** — этап перед HTTP, на котором клиент и сервер согласуют параметры защиты, сервер предъявляет сертификат, а стороны получают общие ключи сеанса.

## Сертификат

> **Сертификат** — публичный документ, связывающий имя сервера с его public key и содержащий срок действия, назначение и имена, для которых он выпущен.

## Private key

> **Private key** — секретный ключ сервера, которым он доказывает владение сертификатом. Его нельзя публиковать, коммитить или включать в архивы и Docker images.

## Certificate Authority

> **Certificate Authority, CA** — доверенный центр сертификации, который подписывает сертификаты сайтов. Браузер доверяет сертификату, если может построить цепочку до известного CA.

## Self-signed certificate

> **Самоподписанный сертификат** — сертификат, подписанный собственным private key, а не доверенным CA. Он шифрует соединение, но браузер не может автоматически подтвердить личность сервера.

## SAN

> **Subject Alternative Name, SAN** — расширение сертификата со списком DNS-имён и IP-адресов, для которых сертификат считается действительным.

## TLS termination

> **TLS termination** — завершение TLS на reverse proxy: Nginx принимает и расшифровывает HTTPS, а во внутренний сервис передаёт обычный HTTP.

## Порты 80 и 443

> Порт `80` обычно используется для HTTP и перенаправления на HTTPS, а порт `443` — для HTTPS/TLS.

## Secure cookie

> Cookie с атрибутом **`Secure`** браузер передаёт только через HTTPS.

## Главные схемы

```text
HTTP  = TCP → HTTP
HTTPS = TCP → TLS handshake → HTTP внутри TLS
```

```text
браузер ──HTTPS/TLS──> Nginx ──HTTP──> FastAPI
```

```text
шифрование: есть
доверие к self-signed сертификату: нет
```

# 2. Подробные объяснения — понять

## 2.1. Что добавляет TLS

Обычный HTTP не защищает содержимое на сетевом участке:

```text
клиент ──HTTP──> сервер
```

HTTPS использует TLS:

```text
клиент ──зашифрованный канал──> сервер
```

TLS решает три задачи:

1. **Конфиденциальность** — посторонний не должен прочитать передаваемые данные.
2. **Целостность** — изменение данных в пути должно обнаруживаться.
3. **Аутентификация сервера** — клиент должен проверить, кому принадлежит сертификат.

Самоподписанный сертификат обеспечивает первые две задачи, но не даёт автоматического доверия к личности сервера.

## 2.2. Упрощённый TLS handshake

Перед HTTP-запросом происходит:

1. Клиент подключается к TCP-порту `443`.
2. Клиент и сервер согласуют поддерживаемую версию TLS и криптографические параметры.
3. Nginx отправляет сертификат.
4. Клиент проверяет имя, срок действия, назначение и цепочку доверия сертификата.
5. Сервер доказывает владение соответствующим private key.
6. Стороны получают симметричные ключи сеанса.
7. HTTP-запросы и ответы передаются внутри защищённого соединения.

Private key не отправляется клиенту. Клиент получает только сертификат и криптографическое доказательство владения ключом.

## 2.3. Почему TLS завершается на Nginx

В Coffee House внешней точкой входа является Nginx:

```text
Интернет
   ↓
Nginx
   ├── React
   └── FastAPI
```

Поэтому сертификат хранится у Nginx, а FastAPI продолжает слушать обычный HTTP на внутреннем порту `8000`:

```text
браузер ──HTTPS──> Nginx ──HTTP──> app:8000
```

Преимущества:

- сертификат настраивается в одном месте;
- backend не занимается TLS;
- `app:8000` остаётся закрытым от внешней сети;
- один reverse proxy может защищать несколько внутренних сервисов;
- сертификат можно заменить без изменения кода FastAPI.

Внутренний HTTP здесь допустим для локальной изолированной Docker-сети. В распределённой недоверенной сети могут потребоваться TLS или mTLS и между сервисами.

## 2.4. Сертификат и private key

Создаются два основных файла:

```text
localhost.crt
→ публичный сертификат

localhost.key
→ секретный private key
```

Nginx использует их так:

```nginx
ssl_certificate /etc/nginx/certs/localhost.crt;
ssl_certificate_key /etc/nginx/certs/localhost.key;
```

Сертификат можно отправлять клиентам. Private key должен оставаться только на сервере.

Если private key раскрыт, злоумышленник может выдавать себя за сервер при наличии подходящих условий. Такой ключ нужно считать скомпрометированным и заменить.

## 2.5. SAN и имя сервера

В локальном сертификате использовались:

```ini
[alt_names]
DNS.1 = localhost
IP.1 = 127.0.0.1
```

Это позволяет проверять сертификат для:

```text
https://localhost
https://127.0.0.1
```

Современные клиенты ориентируются прежде всего на SAN. Одного `CN = localhost` недостаточно для корректного описания всех допустимых имён.

## 2.6. Назначение расширений сертификата

В конфигурации OpenSSL использовались:

```ini
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
```

Смысл:

```text
CA:FALSE
→ сертификат не является центром сертификации

keyUsage
→ разрешённые криптографические операции ключа

serverAuth
→ сертификат предназначен для аутентификации TLS-сервера
```

`critical` означает, что клиент должен понимать и учитывать расширение, иначе сертификат нельзя считать допустимым.

## 2.7. Почему браузер показывает `Not secure`

Самоподписанный сертификат подписан своим же private key:

```text
localhost.crt
→ подписан localhost.key
→ нет цепочки до доверенного CA
```

Поэтому состояние фактически такое:

```text
трафик шифруется: да
имя сервера подтверждено доверенным CA: нет
```

Браузер предупреждает о небезопасности, потому что атакующий теоретически тоже может создать собственный self-signed сертификат для `localhost` или другого имени.

Команда:

```bash
curl -kI https://localhost
```

использует `-k`, то есть отключает проверку доверия к сертификату. Она подтверждает работоспособность TLS и Nginx, но не подтверждает доверенную цепочку.

На реальном сервере используется сертификат доверенного CA, например Let's Encrypt.

## 2.8. Nginx HTTPS server

Основные строки:

```nginx
server {
    listen 443 ssl;
    server_name localhost 127.0.0.1;

    ssl_certificate /etc/nginx/certs/localhost.crt;
    ssl_certificate_key /etc/nginx/certs/localhost.key;

    ssl_protocols TLSv1.2 TLSv1.3;
}
```

Разбор:

```text
listen 443 ssl
→ принимать TLS-соединения на порту 443

server_name
→ имена, для которых применяется server block

ssl_certificate
→ путь к публичному сертификату

ssl_certificate_key
→ путь к private key

TLSv1.2 TLSv1.3
→ разрешены современные версии TLS
```

После TLS handshake внутри этого server block работают обычные `location`, `try_files` и `proxy_pass`.

## 2.9. HTTP → HTTPS redirect

Для HTTP используется отдельный server block:

```nginx
server {
    listen 80;
    server_name localhost 127.0.0.1;

    location = /nginx-health {
        access_log off;
        return 200 "ok\n";
    }

    location / {
        return 301 https://$host$request_uri;
    }
}
```

Запрос:

```text
http://localhost/admin/login
```

получает:

```text
301 Moved Permanently
Location: https://localhost/admin/login
```

`$host` сохраняет имя хоста, а `$request_uri` — путь и query string.

Порт `80` должен быть опубликован, иначе клиент не сможет получить redirect:

```yaml
ports:
  - "80:80"
  - "443:443"
```

## 2.10. Почему healthcheck оставлен на HTTP

Frontend healthcheck выполняется внутри Nginx-контейнера:

```yaml
healthcheck:
  test:
    [
      "CMD",
      "wget",
      "--quiet",
      "--tries=1",
      "--spider",
      "http://localhost/nginx-health"
    ]
```

Специальный `/nginx-health` возвращает `200` без redirect.

Причины:

- self-signed сертификат не доверен `wget` по умолчанию;
- healthcheck должен проверять, что процесс Nginx принимает запросы;
- отдельный URI не зависит от React и FastAPI.

Это liveness-проверка самого Nginx, а не проверка всей бизнес-системы.

## 2.11. Подключение сертификатов через bind mount

Compose:

```yaml
volumes:
  - ./certs:/etc/nginx/certs:ro
```

Означает:

```text
./certs на хосте
→ /etc/nginx/certs внутри контейнера
→ read-only
```

Сертификаты не копируются в Docker image layer. Их можно заменить на хосте и пересоздать контейнер без пересборки frontend-кода.

`:ro` не позволяет Nginx изменять или удалять файлы.

## 2.12. `EXPOSE` и публикация портов

Во frontend Dockerfile:

```dockerfile
EXPOSE 80 443
```

Это документация образа.

Реальная публикация выполняется Compose:

```yaml
ports:
  - "80:80"
  - "443:443"
```

Схема записи:

```text
порт хоста : порт контейнера
```

Backend Dockerfile должен описывать:

```dockerfile
EXPOSE 8000
```

но production Compose не публикует его на хост.

## 2.13. Forwarded headers и Uvicorn

После TLS termination:

```text
клиент использовал HTTPS
Nginx подключился к FastAPI по HTTP
```

Nginx передаёт:

```http
X-Forwarded-Proto: https
X-Forwarded-For: client-ip
```

Uvicorn должен принимать эти данные только от доверенного proxy. В изолированной схеме, где `app:8000` не опубликован наружу и доступен через Docker-сеть, использовались:

```text
--proxy-headers
--forwarded-allow-ips=*
```

`*` нельзя бездумно использовать, если backend доступен недоверенным клиентам напрямую. Иначе они смогут подделывать forwarded headers.

## 2.14. Secure-cookie

Production-настройка:

```env
AUTH_COOKIE_SECURE=true
```

означает, что браузер должен отправлять cookie только через HTTPS.

Пока сайт доступен только по HTTP, такая cookie не будет отправляться обычными HTTP-запросами. После настройки HTTPS это ожидаемое и правильное поведение.

Также `HttpOnly` запрещает JavaScript читать cookie, а `SameSite` управляет её отправкой в cross-site сценариях. Эти атрибуты решают разные задачи.

## 2.15. Защита private key

Private key нельзя помещать в:

```text
Git repository
zip-архив проекта
Docker build context
Docker image
публичные логи
```

Полезная схема `.gitignore`:

```gitignore
/certs/*.key
/certs/*.crt
```

Так `openssl.cnf` можно хранить в Git, а сгенерированные ключ и сертификат — нет.

В корневой `.dockerignore`:

```dockerignore
certs/
```

Nginx получает сертификаты через bind mount, поэтому backend build context они не нужны.

Если private key случайно опубликован, его нужно удалить из доступных мест и создать новую пару ключ/сертификат.

## 2.16. Финальная проверка

Проверка конфигурации Nginx:

```bash
docker exec coffee_house_frontend nginx -t
```

Проверка redirect:

```bash
curl -I http://localhost
```

Ожидается:

```text
301 Moved Permanently
Location: https://localhost/
```

Проверка TLS и frontend:

```bash
curl -kI https://localhost
```

Проверка полного пути до FastAPI:

```bash
curl -k https://localhost/health
```

Полная цепочка:

```text
curl/browser
→ TCP 443
→ TLS handshake
→ Nginx расшифровал HTTP
→ location /health
→ proxy_pass app:8000
→ FastAPI response
→ Nginx зашифровал response
→ клиент
```

# 3. Связный ответ для собеседования

> HTTPS — это HTTP внутри TLS. До передачи HTTP клиент и сервер выполняют TLS handshake: согласуют параметры защиты, сервер предъявляет сертификат и доказывает владение соответствующим private key, после чего данные передаются с использованием ключей сеанса.
>
> В нашей схеме TLS termination выполняет Nginx. Клиент подключается к Nginx по HTTPS на порту `443`, а Nginx передаёт расшифрованный HTTP-запрос FastAPI по внутренней Docker-сети на `app:8000`. Порт `80` используется только для redirect на HTTPS. Сертификат и private key подключаются в Nginx через read-only bind mount и не помещаются в Git или Docker image.
>
> Локальный сертификат самоподписанный, поэтому соединение шифруется, но браузер не может построить цепочку доверия до известного CA и показывает предупреждение. На настоящем сервере нужен сертификат доверенного центра, например Let's Encrypt. После включения HTTPS можно безопасно использовать cookie с атрибутом `Secure`.
