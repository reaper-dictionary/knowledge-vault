# Nginx reverse proxy — маршрутизация и заголовки

> [!info] Как пользоваться заметкой  
> **Учи только раздел «Краткие определения».** Остальные разделы нужны, чтобы понимать путь HTTP-запроса через Nginx, читать `location` и диагностировать ошибки `502` и `504`.

---

# 1. Краткие определения — выучить

## Reverse proxy

> **Reverse proxy** — сервер, который принимает внешние запросы от клиентов и передаёт их одному или нескольким внутренним приложениям.

## Upstream

> **Upstream** — внутренний сервис, которому reverse proxy передаёт запрос, например `app:8000`.

## `location`

> **`location`** — правило Nginx, выбирающее обработчик запроса по URI.

## `proxy_pass`

> **`proxy_pass`** — директива Nginx, задающая адрес внутреннего сервиса, которому нужно передать запрос.

## Docker DNS в Nginx

> В адресе `http://app:8000` имя `app` преобразуется Docker DNS во внутренний IP Compose-сервиса `app`.

## SPA fallback

> **SPA fallback** — возврат `index.html` для frontend-маршрутов, которых нет как физических файлов, чтобы их обработал React Router.

## `Host`

> Заголовок **`Host`** сообщает backend имя хоста, к которому обратился клиент.

## `X-Real-IP`

> **`X-Real-IP`** передаёт backend IP клиента, непосредственно подключившегося к Nginx.

## `X-Forwarded-For`

> **`X-Forwarded-For`** содержит цепочку клиентских и proxy-адресов, через которые прошёл запрос.

## `X-Forwarded-Proto`

> **`X-Forwarded-Proto`** сообщает backend исходную схему запроса клиента: `http` или `https`.

## Proxy timeouts

> `proxy_connect_timeout`, `proxy_send_timeout` и `proxy_read_timeout` ограничивают ожидание соединения, отправки запроса и чтения ответа от upstream.

## Главная схема

```text
Клиент → Nginx → выбор location
                  ├── статический файл или React
                  └── proxy_pass → FastAPI
```

```text
GET /api/v1/products
→ Nginx
→ http://app:8000/api/v1/products
→ FastAPI
```

# 2. Подробные объяснения — понять

## 2.1. Зачем нужен reverse proxy

Без reverse proxy клиент мог бы обращаться напрямую к разным портам:

```text
frontend → localhost:3000
backend  → localhost:8000
```

С reverse proxy появляется одна внешняя точка входа:

```text
клиент → Nginx:80/443
              ├── React
              └── FastAPI
```

Преимущества:

- наружу не публикуется `app:8000`;
- frontend и API доступны с одного origin;
- TLS настраивается в одном месте;
- Nginx может добавлять заголовки, timeout, кеширование и ограничения;
- внутренний IP FastAPI скрыт от клиента.

## 2.2. Где задаётся передача запроса в FastAPI

Главная строка:

```nginx
proxy_pass http://app:8000;
```

Она означает:

```text
передать запрос сервису app на внутренний порт 8000
```

`app` — имя сервиса в Compose:

```yaml
services:
  app:
```

Nginx и `app` подключены к сети `edge`, поэтому Docker DNS может преобразовать имя:

```text
app → внутренний IP контейнера
```

Конкретный IP не указывают, потому что после пересоздания контейнера он может измениться.

## 2.3. Как `location` выбирает backend-маршруты

Пример:

```nginx
location ~ ^/(api|auth|users|health)(/|$) {
    proxy_pass http://app:8000;
    include /etc/nginx/proxy_params.conf;
}
```

Разбор регулярного выражения:

```text
~
→ используется regular expression с учётом регистра

^
→ начало URI

(api|auth|users|health)
→ одна из разрешённых веток

(/|$)
→ после имени должен быть `/` или конец строки
```

Подойдут:

```text
/api/v1/products
/auth/login
/users/me
/health
/health/db
```

Не подойдёт:

```text
/healthcare
```

потому что после `health` нет `/` или конца строки.

## 2.4. Почему `/admin` разделён

В проекте существуют frontend- и backend-маршруты с общим префиксом `/admin`:

```text
/admin/login
→ React

/admin/customer-requests
→ FastAPI
```

Поэтому нельзя отправлять в backend весь `/admin/*`.

Используется точная ветка:

```nginx
location ~ ^/admin/customer-requests(/|$) {
    proxy_pass http://app:8000;
    include /etc/nginx/proxy_params.conf;
}
```

Это сохраняет React-маршруты вроде `/admin/login` и проксирует только административный API customer requests.

## 2.5. Сохраняется ли исходный URI

Конфигурация:

```nginx
proxy_pass http://app:8000;
```

не содержит URI после порта. Поэтому исходный путь сохраняется:

```text
/api/v1/products
→ http://app:8000/api/v1/products
```

Если использовать другую форму `proxy_pass` с URI, Nginx может заменить совпавшую часть пути. Поэтому наличие или отсутствие завершающего `/` и URI в `proxy_pass` имеет значение.

## 2.6. Как Nginx отдаёт React

Типовая конфигурация:

```nginx
root /usr/share/nginx/html;
index index.html;

location /assets/ {
    try_files $uri =404;
}

location / {
    try_files $uri $uri/ /index.html;
}
```

Для реального файла:

```text
/assets/app.js
→ Nginx находит файл
→ возвращает его напрямую
```

Для frontend-маршрута:

```text
/admin/login
→ физического файла нет
→ Nginx возвращает index.html
→ React Router показывает нужную страницу
```

Это и есть SPA fallback.

## 2.7. Зачем вынесли proxy-параметры в отдельный файл

Вместо повторения одинаковых строк в каждом `location` используется:

```nginx
include /etc/nginx/proxy_params.conf;
```

Файл хранит общие настройки:

```nginx
proxy_http_version 1.1;
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_connect_timeout 5s;
proxy_send_timeout 30s;
proxy_read_timeout 30s;
proxy_redirect off;
```

Преимущество:

```text
изменение одного параметра
→ применяется ко всем backend-location
```

Файл должен лежать внутри frontend build context и копироваться в Nginx image:

```dockerfile
COPY proxy_params.conf /etc/nginx/proxy_params.conf
```

## 2.8. `proxy_http_version 1.1`

```nginx
proxy_http_version 1.1;
```

Это версия HTTP во втором соединении:

```text
Nginx → FastAPI
```

Она не обязательно совпадает с версией протокола между браузером и Nginx. HTTP/1.1 поддерживает keep-alive и нужен для корректного WebSocket proxy при добавлении заголовков Upgrade.

## 2.9. Заголовок `Host`

```nginx
proxy_set_header Host $host;
```

Передаёт FastAPI исходное имя хоста клиента:

```text
клиент обратился к coffee.example.com
→ FastAPI получает Host: coffee.example.com
```

Без явной настройки backend может увидеть внутреннее имя upstream или другое значение, сформированное Nginx.

## 2.10. `X-Real-IP` и `X-Forwarded-For`

```nginx
proxy_set_header X-Real-IP $remote_addr;
```

`$remote_addr` — IP непосредственного клиента Nginx.

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

`$proxy_add_x_forwarded_for` добавляет текущий `$remote_addr` к существующей цепочке.

Разница:

```text
X-Real-IP
→ один непосредственный адрес

X-Forwarded-For
→ цепочка клиента и промежуточных proxy
```

Эти заголовки нужны для логов, аудита и rate limiting. Backend должен доверять им только от известных reverse proxy, потому что внешний клиент может подделать собственный `X-Forwarded-For`.

## 2.11. `X-Forwarded-Proto`

```nginx
proxy_set_header X-Forwarded-Proto $scheme;
```

После TLS termination соединения выглядят так:

```text
клиент ──HTTPS──> Nginx ──HTTP──> FastAPI
```

FastAPI видит внутреннее HTTP-соединение и без заголовка не знает, что клиент использовал HTTPS.

Nginx передаёт:

```http
X-Forwarded-Proto: https
```

Это важно для корректных redirect, абсолютных URL и логики Secure-cookie.

## 2.12. Proxy timeouts

```nginx
proxy_connect_timeout 5s;
```

Сколько ждать установки TCP-соединения `Nginx → app:8000`.

```nginx
proxy_send_timeout 30s;
```

Максимально допустимая пауза при отправке запроса upstream.

```nginx
proxy_read_timeout 30s;
```

Максимально допустимая пауза между операциями чтения ответа upstream.

Упрощённо:

```text
не удалось подключиться к app
→ часто 502 Bad Gateway

app подключён, но слишком долго не отвечает
→ часто 504 Gateway Timeout
```

Timeout не всегда означает общий максимальный срок всего запроса: многие директивы измеряют паузу между операциями ввода-вывода.

## 2.13. `proxy_redirect off`

```nginx
proxy_redirect off;
```

Отключает автоматическое переписывание Nginx заголовков `Location` и `Refresh` из ответа upstream.

В схеме с единым внешним origin это делает redirect backend более предсказуемыми, но при сложной маршрутизации правило нужно выбирать осознанно.

## 2.14. Почему FastAPI не публикуется наружу

Production Compose не содержит:

```yaml
app:
  ports:
    - "8000:8000"
```

Но Nginx всё равно обращается к:

```text
app:8000
```

Потому что связь идёт внутри Docker-сети, а не через хост.

Проверка:

```text
https://localhost/health
→ работает через Nginx

http://localhost:8000/health
→ connection refused с хоста
```

Это уменьшает поверхность атаки и не позволяет обходить Nginx.

## 2.15. Проверка Nginx

Проверка синтаксиса:

```bash
docker exec coffee_house_frontend nginx -t
```

Проверка frontend:

```bash
curl -kI https://localhost
```

Проверка полного proxy-маршрута:

```bash
curl -k https://localhost/health
```

Если frontend отвечает, а `/health` даёт `502`, нужно проверять:

```text
запущен ли app
слушает ли app порт 8000
есть ли общая сеть edge
правильно ли указано имя app
что показывают логи Nginx и FastAPI
```

# 3. Связный ответ для собеседования

> Nginx работает как reverse proxy и является единственной внешней точкой входа. Он принимает запрос, выбирает подходящий `location` и либо отдаёт статический React-файл, либо передаёт запрос FastAPI через `proxy_pass http://app:8000`. Имя `app` разрешается Docker DNS, потому что Nginx и FastAPI находятся в общей сети `edge`.
>
> Backend-маршруты выделяются точными правилами, например `/api`, `/auth`, `/users`, `/health` и `/admin/customer-requests`, а остальные пути получают `index.html` для React Router. Общие proxy-настройки вынесены в `proxy_params.conf`.
>
> Nginx передаёт backend исходный `Host`, IP клиента, цепочку proxy и исходную схему через `X-Forwarded-*`. FastAPI не публикуется на хосте: доступ к `app:8000` есть только у контейнеров внутренней Docker-сети. Это уменьшает поверхность атаки и не позволяет клиенту обходить reverse proxy.
