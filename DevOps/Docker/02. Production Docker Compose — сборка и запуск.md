# Production Docker Compose — сборка и запуск

> [!info] Как пользоваться заметкой  
> **Учи только раздел «Краткие определения».** Остальные разделы нужны, чтобы понимать production-конфигурацию, разбирать ошибки запуска и отвечать на уточняющие вопросы на собеседовании.

---

# 1. Краткие определения — выучить

## Development и production Compose

> **Development Compose** — конфигурация для разработки: bind mount исходного кода, hot reload, дополнительные опубликованные порты и инструменты отладки. **Production Compose** — конфигурация для стабильного запуска собранных образов без изменения кода внутри контейнера.

## Multi-stage build

> **Multi-stage build** — Dockerfile с несколькими стадиями, где зависимости собираются в builder-стадии, а в runtime-образ копируется только то, что нужно для запуска.

## Build context

> **Build context** — каталог, содержимое которого Docker может использовать в командах `COPY` и `ADD` во время сборки образа.

## `.dockerignore`

> **`.dockerignore`** — файл, исключающий ненужные и секретные файлы из build context: `.git`, `.env`, тесты, архивы, сертификаты и другие данные, не нужные образу.

## `env_file`

> **`env_file`** передаёт переменные окружения внутрь контейнера. Имя `.env.prod` само по себе не даёт защиты: это обычный текстовый файл, который нельзя коммитить.

## Named volume

> **Named volume** — управляемое Docker постоянное хранилище, которое переживает пересоздание контейнера и используется для данных PostgreSQL, Redis и других stateful-сервисов.

## Bind mount

> **Bind mount** — подключение конкретного файла или каталога хоста внутрь контейнера, например `./certs:/etc/nginx/certs:ro`.

## Docker network

> **Docker network** — виртуальная сеть, в которой контейнеры находят друг друга через Docker DNS по именам Compose-сервисов.

## `ports` и `EXPOSE`

> **`ports`** реально публикует порт контейнера на хосте. **`EXPOSE`** только документирует, какие порты слушает приложение внутри образа, и сам ничего не публикует.

## `depends_on`

> **`depends_on`** задаёт порядок запуска зависимых сервисов. Условия `service_healthy` и `service_completed_successfully` позволяют ждать успешного healthcheck или завершения одноразовой задачи.

## Migration service

> **Migration service** — одноразовый контейнер, который выполняет `alembic upgrade head` и завершается с кодом `0` до запуска приложения и workers.

## Healthcheck

> **Healthcheck** — команда внутри контейнера, по exit code которой Docker определяет состояние `healthy` или `unhealthy`.

## Resource limits

> `mem_limit`, `cpus` и `pids_limit` ограничивают память, процессорное время и количество процессов/потоков контейнера.

## Container hardening

> **Container hardening** — уменьшение возможностей контейнера: запуск не от root, `read_only`, `tmpfs`, `cap_drop: ALL` и `no-new-privileges`.

## Log rotation

> **Log rotation** ограничивает размер Docker-логов и количество сохранённых файлов, чтобы они не заполнили диск.

## Главные схемы

```text
Development → исходники через bind mount → reload → удобная отладка
Production  → собранный image → без исходников с хоста → стабильный запуск
```

```text
db healthy
→ migrate: alembic upgrade head
→ migrate exited 0
→ app и workers запускаются
```

```text
Интернет → frontend/Nginx:80,443
app → db, redis
workers → db, kafka
```

# 2. Подробные объяснения — понять

## 2.1. Зачем разделять development и production

В development важна скорость изменения кода:

```yaml
volumes:
  - .:/app
command: uvicorn src.main:app --reload
```

Изменение файла на хосте сразу видно в контейнере, а Uvicorn автоматически перезапускается.

В production это нежелательно:

- контейнер должен запускать заранее собранный и проверенный код;
- исходники хоста не должны неожиданно менять работающий контейнер;
- `--reload` создаёт лишние процессы и не предназначен для production;
- образ должен быть воспроизводимым: одинаковый image запускает одинаковый код.

Поэтому production-конфигурация использует `Dockerfile.prod`, не подключает корень проекта как volume и запускает обычный Uvicorn без reload.

## 2.2. Multi-stage `Dockerfile.prod`

Типовая схема Python-образа:

```text
builder
→ создаёт virtual environment
→ устанавливает requirements.prod.txt

runtime
→ создаёт non-root пользователя
→ копирует virtual environment
→ копирует src, migrations и alembic.ini
→ запускает приложение
```

Builder может содержать инструменты сборки, а runtime остаётся меньше и безопаснее. Тестовые зависимости вроде `pytest` и `ruff` нужны CI, но обычно не нужны работающему приложению.

`requirements.prod.txt` и CI решают разные задачи:

```text
CI image/environment → тесты, линтеры, проверки
Production image     → только runtime-зависимости
```

## 2.3. Build context и расположение файлов

Если frontend собирается так:

```yaml
build:
  context: ./frontend
  dockerfile: Dockerfile
```

то `frontend/Dockerfile` видит только файлы внутри `./frontend`.

Правильно:

```text
frontend/
├── Dockerfile
├── nginx.conf
└── proxy_params.conf
```

Неправильно ожидать, что frontend Dockerfile сможет выполнить:

```dockerfile
COPY proxy_params.conf /etc/nginx/proxy_params.conf
```

если `proxy_params.conf` лежит в корне проекта выше build context.

## 2.4. `.dockerignore` и секреты

Build context отправляется Docker daemon перед сборкой. Даже если файл не копируется явной командой `COPY`, его не следует включать в context без необходимости.

Обычно исключают:

```dockerignore
.git/
.env
.env.*
__pycache__/
.pytest_cache/
tests/
*.zip
certs/
```

Это уменьшает context, ускоряет сборку и снижает риск попадания секретов в image layer или metadata сборки.

## 2.5. Сети `edge` и `backend`

Production-сервисы полезно разделять по назначению:

```yaml
networks:
  edge:
  backend:
```

Пример подключения:

```text
frontend → edge
app      → edge + backend
db       → backend
redis    → backend
kafka    → backend
workers  → backend
```

Получается:

```text
frontend → app:8000
app → db:5432
app → redis:6379
workers → kafka:9093
```

Frontend не может напрямую обращаться к PostgreSQL, Redis или Kafka, потому что не подключён к `backend`.

## 2.6. Почему внутренним сервисам не нужны `ports`

Контейнеры в общей Docker-сети обращаются друг к другу по внутренним адресам:

```text
app → db:5432
app → redis:6379
worker → kafka:9093
```

Для этого `ports` не требуется. Публикация нужна только клиенту с хоста или из внешней сети.

Production-схема:

```text
публикуются: frontend 80 и 443
не публикуются: app 8000, db 5432, redis 6379, kafka
```

Для временного административного доступа к PostgreSQL можно использовать отдельный override:

```yaml
services:
  db:
    ports:
      - "127.0.0.1:5432:5432"
```

Привязка к `127.0.0.1` не открывает базу на внешних интерфейсах хоста.

## 2.7. `.env`, `.env.prod` и interpolation

Файл `.env.prod` удобен для разделения окружений:

```text
.env       → development
.env.prod  → production
```

Но название файла не делает его безопасным. Оба файла содержат обычный текст и должны быть исключены из Git.

Важно различать два механизма Compose:

```yaml
env_file:
  - .env.prod
```

передаёт значения внутрь контейнера.

А запись:

```yaml
environment:
  POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
```

интерполируется самим Compose до создания контейнера. Для `${...}` Compose берёт значения из shell, стандартного `.env` или явно указанного `--env-file`, а не автоматически из service-level `env_file`.

Чтобы не смешивать источники, для PostgreSQL можно оставить только:

```yaml
env_file:
  - .env.prod
```

если файл содержит все `POSTGRES_*`.

## 2.8. Почему изменение `POSTGRES_PASSWORD` не меняет старую базу

Официальный PostgreSQL image использует `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB` при первой инициализации пустого каталога данных.

Если named volume уже содержит базу:

```text
изменили POSTGRES_PASSWORD в .env.prod
→ контейнер увидел старый volume
→ пользователь PostgreSQL сохранил старый пароль
→ приложение получает InvalidPasswordError
```

Поэтому development и production должны иметь разные volumes:

```text
dev  → coffee_house_postgres_data
prod → coffee_house_prod_postgres_data
```

То же разделение полезно для Redis.

## 2.9. Миграции как отдельный сервис

Неправильная схема:

```text
app command = alembic upgrade head && uvicorn ...
```

При нескольких replicas каждый экземпляр приложения может одновременно попытаться выполнить миграции.

Правильная схема:

```yaml
migrate:
  command: alembic upgrade head
  depends_on:
    db:
      condition: service_healthy
  restart: "no"
```

А приложение ждёт:

```yaml
depends_on:
  migrate:
    condition: service_completed_successfully
```

Состояние:

```text
migrate Exited (0)
```

означает успешное выполнение одноразовой задачи, а не поломку.

Если таблица отсутствует, проверяют:

```bash
docker logs coffee_house_migrate
docker compose run --rm migrate alembic current
docker compose run --rm migrate alembic upgrade head
```

## 2.10. Resource limits

Пример:

```yaml
mem_limit: 250m
cpus: 0.75
pids_limit: 200
```

`mem_limit` — жёсткий потолок памяти. При превышении контейнер может быть завершён OOM killer.

`cpus` ограничивает долю CPU-времени. При достижении лимита контейнер обычно замедляется, а не завершается.

`pids_limit` ограничивает процессы и потоки внутри контейнера. Это защита от fork bomb, утечки потоков и бесконтрольного создания subprocess.

Лимиты выбирают по наблюдаемому пику с запасом, оставляя ресурсы операционной системе и Docker.

## 2.11. Container hardening

Для Python-приложения и workers использовалась схема:

```yaml
read_only: true

tmpfs:
  - /tmp:size=64m,mode=1777

cap_drop:
  - ALL

security_opt:
  - no-new-privileges:true
```

Смысл:

```text
read_only
→ корневая файловая система контейнера недоступна для записи

tmpfs /tmp
→ временная writable-область в памяти

cap_drop: ALL
→ удаление Linux capabilities

no-new-privileges
→ процесс не может получить дополнительные привилегии через exec
```

Также runtime-образ должен запускать приложение от отдельного non-root пользователя.

## 2.12. Логи, restart policy и healthcheck

Ограничение Docker-логов:

```yaml
logging:
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
```

Это даёт максимум примерно три файла по 10 MiB на контейнер.

`restart: unless-stopped` перезапускает завершившийся контейнер, кроме случая, когда администратор остановил его вручную.

Healthcheck меняет состояние контейнера на `healthy` или `unhealthy`, но сам по себе обычно не перезапускает процесс, который продолжает работать. Restart policy реагирует прежде всего на завершение основного процесса.

## 2.13. Короткие команды управления

Удобно скрыть production-команды в `Makefile`:

```makefile
prod-up:
	docker compose -f compose.prod.yml up -d --build

prod-down:
	docker compose -f compose.prod.yml down

prod-ps:
	docker compose -f compose.prod.yml ps

prod-logs:
	docker compose -f compose.prod.yml logs -f
```

Тогда используются короткие команды:

```bash
make prod-up
make prod-ps
make prod-logs
make prod-down
```

# 3. Связный ответ для собеседования

> Development Compose ориентирован на удобство разработки: bind mounts, reload и дополнительные опубликованные порты. Production Compose запускает заранее собранные immutable images без подключения исходников с хоста. Для Python-приложения используется multi-stage Dockerfile: зависимости устанавливаются в builder-стадии, а runtime запускается от non-root пользователя и содержит только необходимые файлы.
>
> Сервисы разделены на сети `edge` и `backend`. Наружу публикуются только порты reverse proxy, а FastAPI, PostgreSQL, Redis и Kafka доступны по именам Compose-сервисов внутри Docker-сетей. Миграции вынесены в одноразовый сервис `migrate`; приложение и workers запускаются только после его успешного завершения.
>
> Для production задаются лимиты памяти, CPU и PID, read-only filesystem, tmpfs для `/tmp`, удаление capabilities, запрет повышения привилегий, restart policy и ротация Docker-логов. Секреты хранятся вне Git, а development и production используют разные named volumes, чтобы данные и учётные данные окружений не смешивались.
