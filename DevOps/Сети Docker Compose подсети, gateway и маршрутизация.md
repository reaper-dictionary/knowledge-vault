
## Термины для заучивания

### IPv4-адрес

**IPv4-адрес** — 32-битный адрес сетевого интерфейса.

Пример:

```text
172.20.0.5
```

### CIDR

**CIDR** указывает, сколько первых битов IP-адреса относятся к сети.

Пример:

```text
172.20.0.5/16
```

Здесь:

```text
16 бит — сетевая часть
16 бит — host-часть
```

### Подсеть

**Подсеть** — логическая часть IP-сети, границы которой определяются IP-адресом и маской/CIDR.

Главный вопрос:

```text
Адрес назначения находится в моей локальной сети
или пакет нужно передать маршрутизатору?
```

### Network address

**Network address** — адрес, обозначающий всю подсеть.

Для:

```text
192.168.50.0/24
```

network address:

```text
192.168.50.0
```

### Broadcast address

**Broadcast address** — специальный IPv4-адрес для обращения ко всем узлам подсети.

Для:

```text
192.168.50.0/24
```

broadcast:

```text
192.168.50.255
```

### Host range

**Host range** — диапазон адресов, которые можно назначать обычным сетевым интерфейсам.

Для:

```text
192.168.50.0/24
```

диапазон:

```text
192.168.50.1–192.168.50.254
```

### Gateway

**Gateway**, или шлюз, — следующий маршрутизатор, которому узел передаёт пакеты для других сетей.

Gateway не является конечным получателем пакета.

### Routing table

**Routing table** — таблица правил, по которым ядро выбирает путь для пакета.

Базовая модель:

```text
получатель в моей подсети
→ отправить напрямую

получатель в другой подсети
→ отправить через gateway
```

### Default route

**Default route** — запасной маршрут, который используется, если не найден более точный маршрут.

Пример:

```text
default via 172.20.0.1 dev eth0
```

### Network namespace

**Network namespace** — изолированное сетевое пространство процесса.

В нём находятся:

- сетевые интерфейсы;
    
- IP-адреса;
    
- таблица маршрутизации;
    
- сокеты;
    
- firewall-правила;
    
- neighbor table.
    

Контейнер Docker использует отдельный network namespace.

## IPv4 и CIDR

Запись:

```text
172.20.0.10/24
```

описывает одновременно:

- IP конкретного интерфейса;
    
- границу сети.
    

Для `/24`:

```text
172.20.0 | 10
сеть       host
```

Сам IP без маски не показывает, где проходит граница сети.

Например:

```text
app:   172.20.0.10/24
redis: 172.20.0.25/24
```

Оба адреса находятся в подсети:

```text
172.20.0.0/24
```

## Расчёт границ подсети

### Подсеть `/24`

```text
192.168.50.0/24
```

Результат:

```text
Network:   192.168.50.0
Broadcast: 192.168.50.255
Hosts:     192.168.50.1–192.168.50.254
```

### Подсеть `/26`

У `/26` остаётся шесть host-бит:

```text
32 - 26 = 6
2^6 = 64 адреса
```

Блоки идут по 64 адреса:

```text
0–63
64–127
128–191
192–255
```

Для адреса:

```text
192.168.10.140/26
```

число `140` попадает в блок `128–191`.

Результат:

```text
Network:   192.168.10.128
Broadcast: 192.168.10.191
Hosts:     192.168.10.129–192.168.10.190
```

## Реальная сеть Coffee House

Docker Compose автоматически создал сеть:

```text
coffee_house_default
```

Её параметры:

```text
Subnet:  172.20.0.0/16
Gateway: 172.20.0.1
Driver:  bridge
```

Контейнеры:

```text
redis:                  172.20.0.2/16
kafka:                  172.20.0.3/16
db:                     172.20.0.4/16
app:                    172.20.0.5/16
outbox_publisher:       172.20.0.6/16
notification_consumer:  172.20.0.7/16
frontend:               172.20.0.8/16
```

Все контейнеры находятся в одной подсети:

```text
172.20.0.0/16
```

Поэтому между ними используется локальный маршрут через Docker bridge.

Пример:

```text
app 172.20.0.5
→ Docker bridge
→ db 172.20.0.4
```

Gateway `172.20.0.1` для этого пути не требуется.

## Автоматическая сеть Docker Compose

Если в Compose не указан раздел `networks`, Compose создаёт сеть:

```text
<project>_default
```

Для Coffee House:

```text
coffee_house_default
```

Docker автоматически:

1. создаёт bridge-сеть;
    
2. выбирает подсеть;
    
3. назначает gateway;
    
4. подключает контейнеры;
    
5. выдаёт им IP-адреса;
    
6. создаёт маршруты в их network namespace.
    

Поэтому отсутствие явного параметра `gateway` в Compose не означает отсутствие gateway.

## Маршрут внутри контейнера app

Таблица маршрутизации процесса приложения:

```text
default via 172.20.0.1 dev eth0
172.20.0.0/16 dev eth0 proto kernel scope link src 172.20.0.5
```

### Локальный маршрут

```text
172.20.0.0/16 dev eth0
```

Значение:

```text
если адрес назначения входит в 172.20.0.0/16
→ отправить пакет через eth0
```

Например:

```text
app 172.20.0.5
→ db 172.20.0.4
```

### Default route

```text
default via 172.20.0.1 dev eth0
```

Значение:

```text
если более точного маршрута нет
→ передать пакет gateway 172.20.0.1
```

Например:

```text
app
→ gateway 172.20.0.1
→ сетевой стек Docker-хоста
→ NAT
→ внешняя сеть
→ 8.8.8.8
```

## Разбор полей `ip route`

Строка:

```text
172.20.0.0/16 dev eth0 proto kernel scope link src 172.20.0.5
```

### `dev eth0`

Использовать сетевой интерфейс:

```text
eth0
```

### `proto kernel`

Маршрут автоматически добавило ядро Linux после назначения интерфейсу IP-адреса.

Это не означает сетевой протокол вроде TCP или UDP.

Здесь `proto` обозначает происхождение записи маршрута.

### `scope link`

Сеть доступна непосредственно через сетевой интерфейс.

Для доставки к ней не нужен промежуточный IP-gateway.

### `src 172.20.0.5`

Предпочтительный исходный IP для пакетов, отправляемых по этому маршруту.

При запросе от `app` к `db`:

```text
source:      172.20.0.5
destination: 172.20.0.4
```

## Почему `ip route` показывает только адрес app

Таблица маршрутизации не является списком контейнеров.

Строка:

```text
172.20.0.0/16 dev eth0
```

сразу покрывает всю подсеть:

```text
172.20.0.0–172.20.255.255
```

Поэтому отдельные маршруты для Redis, Kafka, PostgreSQL и frontend не нужны.

Адрес:

```text
src 172.20.0.5
```

показывает собственный IP контейнера `app`, из network namespace которого выполнялась команда.

Для просмотра известных локальных соседей используется отдельная neighbor table:

```bash
ip neigh
```

## Контейнер и процесс Linux

Контейнер не является отдельной виртуальной машиной.

В основе контейнера находятся обычные процессы Linux, изолированные через:

- namespaces;
    
- cgroups;
    
- capabilities;
    
- filesystem isolation.
    

Ссылки на namespaces процесса находятся в:

```text
/proc/<PID>/ns/
```

Network namespace:

```text
/proc/<PID>/ns/net
```

Можно войти в network namespace процесса и выполнить там команду хостовой системы:

```bash
sudo nsenter -t <PID> -n ip route
```

Параметры:

```text
-t <PID> — выбрать процесс
-n       — войти в его network namespace
```


## Типовые ошибки

### Ошибка: считать подсеть списком работающих контейнеров

Неверно:

```text
172.20.0.0/16 показывает все контейнеры
```

Правильно:

```text
172.20.0.0/16 задаёт диапазон адресов и маршрут к этой сети
```

### Ошибка: считать routing table списком соседей

Routing table отвечает:

```text
куда отправить пакет
```

Она не отвечает:

```text
какие конкретные контейнеры сейчас существуют
```

### Ошибка: считать, что gateway участвует во всех соединениях

Для контейнеров одной подсети:

```text
app → db
```

Gateway не является промежуточным IP-узлом.

Для внешнего адреса:

```text
app → gateway → внешняя сеть
```

### Ошибка: считать, что gateway отсутствует без настройки Compose

Compose и Docker обычно создают gateway автоматически для bridge-сети.

### Ошибка: считать `proto kernel` сетевым протоколом

В выводе `ip route` поле `proto` показывает источник маршрута.

```text
proto kernel
```

означает, что запись создало ядро.

### Ошибка: считать отсутствие команды `ip` сетевой проблемой

Ошибка:

```text
exec: "ip": executable file not found in $PATH
```

означает, что утилита `ip` не установлена внутри образа.

Это не означает, что у контейнера отсутствует сеть.

Вместо установки диагностических пакетов в runtime-контейнер можно использовать:

```bash
sudo nsenter -t <PID> -n ip route
```
