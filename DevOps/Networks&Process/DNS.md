
## Основные термины для заучивания

> [!abstract] Главное определение  
> **DNS (Domain Name System)** — распределённая система, которая сопоставляет доменные имена с IP-адресами и хранит другие служебные записи домена.

### Участники DNS

|Термин|Короткое определение|
|---|---|
|**Доменное имя**|Понятное человеку имя ресурса, например `api.example.com`.|
|**DNS-запрос**|Вопрос DNS-серверу о конкретном имени и типе записи.|
|**DNS-ответ**|Результат запроса: нужная запись, перенаправление либо сообщение об отсутствии данных.|
|**Stub resolver**|Компонент на компьютере, который принимает имя от приложения и передаёт запрос настроенному DNS-резолверу.|
|**Recursive resolver**|DNS-сервер, который ищет ответ за клиента и кэширует результат.|
|**Root DNS-сервер**|Указывает, где находятся DNS-серверы доменной зоны верхнего уровня, например `.com`.|
|**TLD-сервер**|Указывает, какие authoritative-серверы отвечают за домен внутри зоны, например `example.com`.|
|**Authoritative DNS-сервер**|Хранит официальные DNS-записи конкретного домена и отвечает за них.|
|**DNS-кэш**|Временно сохранённая копия ранее полученного DNS-ответа.|
|**TTL**|Время, в течение которого DNS-запись разрешено хранить в кэше. По смыслу похоже на TTL в Redis.|

### Основные DNS-записи

|   |   |
|---|---|
|Запись|Что хранит|
|**A**|IPv4-адрес имени.|
|**AAAA**|IPv6-адрес имени.|
|**CNAME**|Псевдоним: указывает на другое доменное имя, а не на IP.|
|**NS**|Authoritative DNS-серверы домена.|
|**MX**|Почтовые серверы домена.|
|**TXT**|Служебный текст: подтверждение владения доменом, настройки почты и другие данные.|

### Результаты поиска

|   |   |
|---|---|
|Термин|Значение|
|**NOERROR**|DNS-запрос обработан без ошибки.|
|**NXDOMAIN**|Запрошенного доменного имени не существует.|
|**NODATA**|Имя существует, но записи запрошенного типа у него нет.|
|**Negative caching**|Временное кэширование ответа о том, что имени или записи нет.|

### Транспорт

|   |   |
|---|---|
|Термин|Значение|
|**UDP 53**|Обычный способ передать небольшой DNS-запрос и получить ответ.|
|**TCP 53**|Используется, когда нужен полный большой ответ, а также для некоторых специальных операций DNS.|

> [!important] Формула для запоминания  
> **Root знает, где зона. TLD знает, кто управляет доменом. Authoritative знает записи домена. Recursive resolver проходит эту цепочку за клиентом.**

## Объяснение

### 1. DNS и подключение к сайту — два отдельных обмена

Пусть браузер хочет открыть:

```
https://api.example.com
```

Сначала ему нужен IP-адрес. Для этого происходит отдельный DNS-обмен:

```
компьютер → DNS-сервер: какой IP у api.example.com?
компьютер ← DNS-сервер: 203.0.113.10
```

После получения IP DNS выполнил свою задачу и больше в подключении к сайту не участвует.

Только затем начинается новый обмен уже с сервером сайта:

```
компьютер → 203.0.113.10:443
```

Для обычного HTTPS это может быть TCP → TLS → HTTP. Для HTTP/3 используется QUIC поверх UDP. Это уже не DNS.

> [!warning] Не путать
> 
> - `компьютер ↔ DNS-сервер` — узнать IP;
>     
> - `компьютер ↔ сервер сайта` — получить данные приложения.
>     

### 2. Кто узнаёт IP

Упрощённая цепочка начинается так:

```
приложение
→ stub resolver операционной системы
→ настроенный recursive resolver
```

Приложение просит операционную систему узнать IP. Stub resolver передаёт DNS-запрос настроенному recursive resolver.

Таким resolver может быть:

```
192.168.0.1  — домашний роутер
1.1.1.1      — Cloudflare
8.8.8.8      — Google
```

Если запрос отправлен роутеру, он может сам передать его DNS-серверу провайдера или другому resolver.

### 3. Сначала проверяется кэш

До полного поиска готовый ответ проверяется в кэшах. Упрощённо:

```
1. Кэш приложения
2. Кэш операционной системы
3. Кэш recursive resolver
4. Полный DNS-поиск, только если готового ответа нет
```

Запись хранится не вечно. Её TTL определяет, сколько времени можно использовать сохранённую копию.

Если resolver уже недавно узнал:

```
api.example.com → 203.0.113.10
```

он сразу вернёт этот IP клиенту и не станет заново проходить DNS-иерархию.

### 4. Как проходит полный поиск

Если ответа нет в кэше, recursive resolver ищет его сам.

#### Шаг 1. Root

Resolver спрашивает Root-сервер, где искать домены зоны `.com`.

Root не обязан знать IP `api.example.com`. Он возвращает адреса TLD-серверов зоны `.com`.

#### Шаг 2. TLD

Resolver спрашивает TLD-сервер `.com`, кто отвечает за `example.com`.

TLD-сервер возвращает NS-записи — адреса authoritative-серверов домена `example.com`.

#### Шаг 3. Authoritative

Resolver спрашивает authoritative-сервер, какая запись создана для `api.example.com`.

Тот может вернуть, например:

```
api.example.com → A → 203.0.113.10
```

Resolver кэширует ответ на время TTL и возвращает его компьютеру.

Полная цепочка:

```
компьютер → recursive resolver

recursive resolver → Root
Root → адреса TLD-серверов .com

recursive resolver → TLD .com
TLD .com → authoritative-серверы example.com

recursive resolver → authoritative-сервер example.com
authoritative → запись api.example.com

recursive resolver → компьютер: 203.0.113.10
```

Root и TLD обычно не пересылают запрос дальше сами. Они говорят resolver, к кому обратиться следующим.

### 5. Зачем нужна такая иерархия

Один DNS-сервер не смог бы удобно и надёжно хранить все домены мира. Поэтому ответственность разделена:

```
Root
└── знает серверы зон .com, .org, .ru и других
    └── TLD .com знает серверы доменов внутри .com
        └── владелец example.com управляет записями своего домена
```

Это даёт три главных преимущества:

1. Нет одного огромного центрального справочника со всеми записями.
    
2. Ответственность распределена между разными организациями.
    
3. Владелец домена может самостоятельно менять свои записи.
    

Например, владелец `example.com` может изменить IP `api.example.com`, не обращаясь к администраторам Root или зоны `.com`.

### 6. Типы DNS-записей

#### A — IPv4

```
api.example.com → 203.0.113.10
```

#### AAAA — IPv6

```
api.example.com → 2001:db8::10
```

У одного имени одновременно могут существовать A- и AAAA-записи.

#### CNAME — другое доменное имя

```
www.example.com → CNAME → example.com
example.com     → A     → 203.0.113.10
```

CNAME не содержит IP. Он сообщает, что поиск нужно продолжить для другого доменного имени.

#### NS — кто управляет DNS домена

```
example.com → ns1.provider.com
example.com → ns2.provider.com
```

NS-записи указывают authoritative DNS-серверы домена.

#### MX — куда доставлять почту

```
example.com → MX 10 mail1.example.com
example.com → MX 20 mail2.example.com
```

MX указывает на доменное имя почтового сервера. Меньшее число означает более высокий приоритет. Затем для имени почтового сервера отдельно ищется A- или AAAA-запись.

#### TXT — служебные данные

TXT-записи применяются, например, для:

- подтверждения владения доменом;
    
- настройки SPF, DKIM и других механизмов электронной почты;
    
- передачи служебных данных внешним сервисам.
    

TXT — не текст, который автоматически отображается на сайте.

### 7. Если нужных данных нет

#### NXDOMAIN

```
unknown.example.com не существует вообще
```

Ответ `NXDOMAIN` означает отсутствие самого запрошенного имени.

#### NODATA

```
example.com существует,
но у него нет записи запрошенного типа
```

Например, мы запросили MX, но для существующего домена почта не настроена.

Resolver может временно кэшировать оба отрицательных результата, чтобы не повторять одинаковый поиск при каждом запросе.

### 8. Почему DNS использует UDP и TCP

Обычный DNS-вопрос и ответ небольшие. Поэтому чаще всего используется UDP 53:

```
клиент → DNS-сервер: один вопрос
клиент ← DNS-сервер: один ответ
```

UDP не требует предварительно устанавливать соединение. Если пакет потерялся, запрос можно повторить.

Если полный ответ не помещается в UDP-ответ, сервер может сообщить, что ответ обрезан. Тогда клиент повторяет тот же DNS-запрос через TCP 53 и получает полный результат.

Упрощённо:

```
обычный небольшой DNS-ответ → UDP 53
слишком большой ответ       → повтор через TCP 53
некоторые служебные операции DNS → TCP 53
```

UDP и TCP здесь доставляют DNS-вопрос DNS-серверу. Это не транспорт будущего соединения с сайтом.

### 9. Как читать основной вывод `dig`

Команда:

```
dig example.com A
```

означает: запросить A-запись `example.com`.

Главные части ответа:

```
status: NOERROR
```

Запрос обработан без ошибки.

```
QUESTION SECTION:
example.com.  IN  A
```

Запрашивалась A-запись имени `example.com`.

```
ANSWER SECTION:
example.com.  80  IN  A  172.66.147.243
example.com.  80  IN  A  104.20.23.154
```

Здесь:

- `example.com` — имя;
    
- `80` — оставшийся TTL в секундах;
    
- `A` — тип записи;
    
- два IP — два опубликованных IPv4-адреса.
    

```
SERVER: 192.168.0.1#53 (UDP)
```

Это DNS-сервер, которому компьютер отправил вопрос:

- `192.168.0.1` — IP DNS-сервера, в данном случае роутера;
    
- `53` — порт DNS;
    
- `UDP` — использованный транспорт.
    

Это не IP сайта.

```
Query time: 95 msec
```

Время получения DNS-ответа.

### 10. DNS при деплое на VM

После получения публичного IP VM можно создать A-запись:

```
coffee.example.com → публичный IPv4-адрес VM
```

После распространения записи пользователь сможет выполнить:

```
dig coffee.example.com A
```

и увидеть опубликованный IP.

Если перед VM используется Cloudflare, CDN или внешний балансировщик, DNS может возвращать IP посредника, а не настоящий IP VM:

```
пользователь → Cloudflare или балансировщик → VM
```

Публичный IP сам по себе обычно не считается секретом. Сервер защищают firewall, закрытые порты, TLS, авторизация и своевременные обновления.

DNS сообщает опубликованные записи, но сам по себе не показывает все открытые порты и запущенные приложения.

## Краткий итог

```
1. Приложению нужен IP доменного имени.
2. Stub resolver обращается к recursive resolver.
3. Сначала проверяются кэши.
4. Если ответа нет, resolver проходит Root → TLD → Authoritative.
5. Resolver возвращает запись и кэширует её на время TTL.
6. DNS-обмен заканчивается.
7. Приложение отдельно подключается к найденному IP.
```

> [!success] База DNS  
> DNS — отдельная распределённая система поиска записей. Она помогает приложению получить адрес сервера, но не становится частью последующего соединения с этим сервером.
