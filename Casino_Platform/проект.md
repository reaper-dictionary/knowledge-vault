## Сервисы

### 1. Edge Gateway

Отвечает за:

- REST;
- GraphQL;
- WebSocket connections;
- проверку access token;
- rate limiting;
- агрегацию ответов;
- broadcast сообщений клиентам.

Gateway не должен содержать игровую или финансовую бизнес-логику.

### 2. Identity Service

Отвечает за:

- пользователей;
- авторизацию;
- роли;
- permissions;
- refresh sessions;
- выдачу claims для AI Assistant.

Часть можно извлечь из Void Marketplace.

### 3. Wallet Service

Отдельный источник истины для виртуальных денег:

- balance;
- immutable ledger;
- debit;
- credit;
- reservation;
- settlement;
- idempotency;
- reconciliation.

Ни Casino Service, ни AI Assistant не могут самостоятельно менять баланс в БД.

Пример gRPC-контракта:

```
service WalletService {
  rpc ReserveFunds(ReserveFundsRequest) returns (ReserveFundsResponse);
  rpc SettleBet(SettleBetRequest) returns (SettleBetResponse);
  rpc ReleaseReservation(ReleaseReservationRequest) returns (ReleaseReservationResponse);
  rpc GetBalance(GetBalanceRequest) returns (GetBalanceResponse);
}
```

### 4. Casino Service

Внутри него отдельные модули:

```
casino
├── games
├── rooms
├── rounds
├── bets
├── fairness
├── leaderboards
├── campaigns
├── achievements
└── tournaments
```

Не нужно создавать отдельный микросервис для каждой игры. Это даст много инфраструктуры без пользы.

Каждая игра реализует общий контракт:

```
class GameDefinition(Protocol):
    game_type: str

    def validate_bet(self, bet: BetRequest) -> None: ...
    def create_round(self, context: RoundContext) -> RoundState: ...
    def accept_action(
        self,
        state: RoundState,
        action: PlayerAction,
    ) -> RoundState: ...
    def finish_round(self, state: RoundState) -> RoundResult: ...
    def calculate_payout(self, result: RoundResult) -> list[Payout]: ...
```

Это позволит добавлять новые игры как плагины внутри Casino Service, не размножая сервисы.


# Использование Kafka, Redis и WebSocket

## WebSocket

Используется для:

- подключения игрока;
- входа в комнату;
- отправки игровых команд;
- получения состояния раунда;
- таймеров;
- ставок других игроков;
- координат курьера;
- уведомлений.

Сервер должен быть authoritative:

```
Клиент сообщает намерение.
Сервер проверяет команду.
Сервер изменяет состояние.
Сервер рассылает подтверждённое состояние.
```

Клиент не должен рассчитывать выигрыш, баланс или финальный результат.

## Redis

Используется для:

- presence;
- списка подключений;
- room state cache;
- distributed locks;
- idempotency;
- rate limiting;
- leaderboard;
- Redis Pub/Sub для низколатентной рассылки между экземплярами Gateway.

Потеря сообщения Redis Pub/Sub не должна повреждать данные: клиент должен уметь запросить актуальный snapshot комнаты.

## Kafka

Используется для надёжных domain events:

```
player.registered
room.created
round.started
bet.accepted
round.completed
wallet.reserved
wallet.settled
achievement.unlocked
delivery.location.updated
delivery.completed
assistant.tool.executed
```

Kafka не следует использовать для каждого realtime-тика Crash или каждой GPS-точки, которую нужно немедленно показать пользователю. Для такого трафика лучше Redis/WebSocket, а в Kafka отправлять агрегированные или значимые события.

# 6. Provably fair и RTP

## Provably fair

До начала раунда Casino Service создаёт:

```
server_seed
server_seed_hash
```

Клиент получает hash до начала раунда.

Результат вычисляется детерминированно из:

```
server_seed + client_seed + nonce
```

После завершения раунда сервер раскрывает `server_seed`, и пользователь может воспроизвести расчёт.

Это необходимо применить хотя бы к:

- Crash;
- Dice;
- Coinflip.

## RTP

Нужно сделать отдельный simulation command:

```
python -m tools.simulate_rtp \
  --game crash \
  --rounds 1000000 \
  --seed test-seed
```

Результат:

```
theoretical RTP
empirical RTP
total wagered
total paid
house edge
standard deviation
```

Это не заменяет сертификацию реального казино, но для портфолио показывает, что команда понимает математическую проверку игровой модели.
