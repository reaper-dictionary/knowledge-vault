# Синхронное взаимодействие gRPC и устойчивость

> [!info] Как пользоваться заметкой  
> Сначала выучи определения и таблицу status codes. Затем разберись, почему timeout, retry и idempotency должны проектироваться вместе.

---

# 1. Краткие определения — выучить

## Synchronous request

> **Синхронный запрос** — взаимодействие, при котором вызывающий сервис ждёт ответ другого сервиса, прежде чем продолжить текущую операцию.

## gRPC

> **gRPC** — RPC-фреймворк поверх HTTP/2, обычно использующий Protocol Buffers для строгих контрактов и генерации client/server stubs.

## Deadline

> **Deadline** — абсолютный момент времени, после которого результат вызова больше не нужен. Deadline должен передаваться по цепочке вызовов.

## Timeout

> **Timeout** — максимальное время ожидания конкретной операции. Бесконечный timeout превращает медленный dependency в зависшие запросы и исчерпание ресурсов.

## Retry

> **Retry** — повтор операции после временной ошибки. Retry безопасен только при ограниченном числе попыток, backoff, jitter и понятной идемпотентности.

## Exponential backoff и jitter

> **Exponential backoff** увеличивает паузу между попытками. **Jitter** добавляет случайность, чтобы множество клиентов не повторяли запрос одновременно.

## Idempotency

> **Idempotency** — свойство операции, при котором повтор с тем же ключом не создаёт второй бизнес-эффект.

## Circuit breaker

> **Circuit breaker** — механизм, временно прекращающий вызовы явно нездорового dependency, чтобы система быстрее отвечала ошибкой и успела восстановиться.

## Bulkhead

> **Bulkhead** — изоляция ресурсов: отдельные лимиты соединений, очередей или concurrency не дают одному медленному dependency исчерпать весь сервис.

## Correlation ID

> **Correlation ID** — идентификатор сквозной операции, который передаётся через HTTP, WebSocket, gRPC, Kafka и логи для поиска всей цепочки.

## Главная схема

```text
Gateway: общий budget 800 ms
→ Casino: deadline 650 ms
  → Wallet: deadline 350 ms
    → PostgreSQL: statement timeout < 350 ms
```

Каждый внутренний шаг получает меньший бюджет, чтобы внешний слой успел корректно вернуть ошибку.

# 2. Подробные объяснения — понять

## 2.1. Где gRPC полезен в Casino Platform

Подходящие синхронные вызовы:

```text
Gateway → Identity: Validate/GetUser
Gateway → Casino: PlaceBet/GetSnapshot
Casino → Wallet: ReserveFunds/SettleBet/ReleaseReservation
```

Синхронный вызов создаёт runtime dependency. Если Wallet недоступен, Casino не может безопасно принять ставку. Это нормально: лучше отказать, чем подтвердить ставку без финансовой гарантии.

## 2.2. Contract-first protobuf

```proto
syntax = "proto3";

package wallet.v1;

service WalletService {
  rpc ReserveFunds(ReserveFundsRequest) returns (ReserveFundsResponse);
  rpc SettleBet(SettleBetRequest) returns (SettleBetResponse);
}

message ReserveFundsRequest {
  string request_id = 1;
  string user_id = 2;
  string bet_id = 3;
  int64 amount_minor = 4;
}

message ReserveFundsResponse {
  string reservation_id = 1;
  int64 available_balance_minor = 2;
}
```

Правила совместимости protobuf:

- не менять смысл существующего field number;
- удалённые номера и имена помещать в `reserved`;
- новые необязательные поля добавлять новыми номерами;
- несовместимое изменение выпускать как новую версию package/API;
- деньги передавать целым `int64` в minor units, а не `float`.

## 2.3. Deadline на Python-клиенте

```python
import grpc


async def reserve_funds(stub, command, correlation_id: str):
    request = wallet_pb2.ReserveFundsRequest(
        request_id=str(command.request_id),
        user_id=str(command.user_id),
        bet_id=str(command.bet_id),
        amount_minor=command.amount_minor,
    )

    return await stub.ReserveFunds(
        request,
        timeout=0.35,
        metadata=(("x-correlation-id", correlation_id),),
    )
```

`timeout=0.35` не гарантирует ответ за 350 ms. Он ограничивает ожидание клиента. Сервер должен отменять лишнюю работу, а запросы к БД тоже должны иметь ограничения.

## 2.4. gRPC status codes

| Code | Смысл для домена | Обычно retry? |
|---|---|---|
| `INVALID_ARGUMENT` | неверный amount или формат команды | нет |
| `UNAUTHENTICATED` | нет действительной identity | нет, сначала новая auth |
| `PERMISSION_DENIED` | действие запрещено | нет |
| `NOT_FOUND` | account/reservation не существует | нет |
| `FAILED_PRECONDITION` | стадия операции не позволяет действие | нет |
| `ALREADY_EXISTS` | конфликт уникальности без идемпотентного результата | обычно нет |
| `RESOURCE_EXHAUSTED` | rate/concurrency limit | иногда, с backoff |
| `UNAVAILABLE` | временно недоступен сервис | да, ограниченно |
| `DEADLINE_EXCEEDED` | budget закончился | только если операция идемпотентна и ещё есть общий budget |
| `INTERNAL` | неизвестная серверная ошибка | обычно не вслепую |

Бизнес-ошибку `insufficient funds` удобно отображать в `FAILED_PRECONDITION` с машинно-читаемым error detail, а не возвращать `INTERNAL`.

## 2.5. Почему timeout не означает, что команда не выполнена

```text
Casino → ReserveFunds
Wallet → commit успешен
ответ теряется в сети
Casino → DEADLINE_EXCEEDED
```

Casino не знает, был ли commit. Если он повторит запрос с новым ключом, деньги могут зарезервироваться второй раз. Поэтому повтор использует тот же `request_id`, а Wallet возвращает результат первой операции.

## 2.6. Ограниченный retry

```python
import asyncio
import random
import grpc

RETRYABLE = {
    grpc.StatusCode.UNAVAILABLE,
    grpc.StatusCode.RESOURCE_EXHAUSTED,
}


async def call_with_retry(operation, attempts: int = 3):
    for attempt in range(attempts):
        try:
            return await operation()
        except grpc.aio.AioRpcError as exc:
            last_attempt = attempt == attempts - 1
            if exc.code() not in RETRYABLE or last_attempt:
                raise

            delay = 0.05 * (2**attempt) + random.uniform(0, 0.03)
            await asyncio.sleep(delay)
```

Для `ReserveFunds` это допустимо только при неизменном idempotency key. Нельзя складывать независимые retries на Gateway, Casino, gRPC library и service mesh: количество реальных вызовов перемножится.

## 2.7. Deadline propagation

Если Gateway получил запрос с остатком 600 ms, Casino не должен выдавать Wallet новый timeout 2 s. Он передаёт меньший остаток:

```python
remaining = context.time_remaining()
wallet_timeout = max(0.0, min(0.35, remaining - 0.05))
```

Резерв 50 ms оставляет Casino время преобразовать ошибку и ответить Gateway.

## 2.8. Circuit breaker и bulkhead

Circuit breaker обычно имеет состояния:

```text
CLOSED → вызовы разрешены
ошибок слишком много
OPEN → быстрый отказ без сетевого вызова
через паузу
HALF_OPEN → несколько пробных вызовов
успех → CLOSED; ошибка → OPEN
```

Bulkhead для Wallet client может ограничивать число одновременных RPC. Когда лимит исчерпан, новые запросы быстро получают overload error, а не создают бесконечную очередь.

## 2.9. Correlation ID и логи

```python
logger.info(
    "wallet.reserve.completed",
    extra={
        "correlation_id": correlation_id,
        "request_id": str(command.request_id),
        "bet_id": str(command.bet_id),
        "result": "reserved",
    },
)
```

В логах IDs полезны. В Prometheus labels `user_id`, `bet_id` и `request_id` добавлять нельзя: это создаёт unbounded cardinality.

# 3. Типовые ошибки

### Ошибка: gRPC автоматически делает систему надёжной

gRPC даёт транспорт и контракт. Deadlines, idempotency, retry policy, overload protection и observability проектируются отдельно.

### Ошибка: повторять любую ошибку

Повтор `INVALID_ARGUMENT` или `PERMISSION_DENIED` только создаёт лишнюю нагрузку. `INTERNAL` может скрывать постоянный баг.

### Ошибка: retry с новым request ID

Новый ID превращает повтор в новую бизнес-команду.

### Ошибка: одинаковый timeout на всех уровнях

Внутренний сервис продолжит работу после того, как внешний клиент уже прекратил ждать.

### Ошибка: длинная синхронная цепочка

```text
Gateway → A → B → C → D
```

Латентность и вероятность отказа накапливаются. Цепочку нужно сокращать или отделять реакции событиями.

# 4. Связный ответ для собеседования

> Для синхронных команд между сервисами я использую contract-first gRPC и всегда задаю deadline. Входной time budget уменьшается по цепочке, чтобы верхний сервис успел обработать ошибку. Retry разрешается только для временных status codes, ограничивается по числу попыток и использует backoff с jitter. Для команд с побочным эффектом, например ReserveFunds, повтор безопасен только с тем же idempotency key, потому что timeout не доказывает отсутствие commit. Circuit breaker даёт быстрый отказ при нездоровом dependency, а bulkhead ограничивает влияние перегрузки на остальные операции.
