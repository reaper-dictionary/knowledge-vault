# Границы микросервисов и владение данными

> [!info] Как пользоваться заметкой

# 1. Краткие определения — выучить

## Микросервис

> **Микросервис** — независимо изменяемый и развёртываемый компонент, который владеет конкретной бизнес-возможностью, своими правилами и данными и взаимодействует с другими сервисами через явные контракты.

## Service boundary

> **Service boundary** — граница ответственности сервиса: какие решения он принимает, какими данными владеет и какие операции предоставляет наружу.

## Bounded Context

> **Bounded Context** — область, внутри которой термины и бизнес-правила имеют одно точное значение. Граница микросервиса часто совпадает с Bounded Context, но это не обязательное правило.

## Source of Truth

> **Source of Truth** — единственный сервис, чья версия данных считается правильной и который имеет право изменять эти данные по своим бизнес-правилам.

## Database per service

> **Database per service** — принцип, при котором сервис владеет своей схемой или базой, а другие сервисы не читают и не изменяют её таблицы напрямую.

## Aggregate и invariant

> **Aggregate** — группа связанных объектов, изменяемая как одна согласованная единица. **Invariant** — правило, которое должно оставаться истинным после каждой бизнес-операции.

## Contract

> **Contract** — согласованный формат взаимодействия: HTTP/OpenAPI, gRPC/protobuf, WebSocket envelope или Kafka event schema. Контракт определяет вход, выход, ошибки и правила совместимости.

## Coupling и cohesion

> **Coupling** — степень зависимости сервисов друг от друга. **Cohesion** — насколько тесно обязанности внутри одного сервиса относятся к одной бизнес-цели. Хорошая граница стремится к высокой cohesion и контролируемому coupling.

## Distributed monolith

> **Distributed monolith** — система из нескольких процессов, которые формально называются микросервисами, но не могут независимо изменяться или запускаться из-за общей БД, синхронных цепочек и скрытых зависимостей.

## Data projection

> **Projection** — локальная read-only модель чужих данных, построенная из событий или API. Её можно восстановить; она не становится новым Source of Truth.

## Eventual consistency

> **Eventual consistency** — модель, при которой разные сервисы могут временно видеть разные версии данных, но после доставки и обработки событий приходят к согласованному состоянию.

## Главная схема

```text
Identity → владеет User, Credentials, RefreshSession
Wallet   → владеет Account, Ledger, Reservation, Settlement
Casino   → владеет Room, Round, Bet, GameResult
Gateway  → владеет соединениями, routing и временным presence
```

```text
Чужой user_id можно хранить
Чужую бизнес-сущность изменять нельзя
Нужны данные → API, событие или локальная projection
```

# 2. Подробные объяснения — понять

## 2.1. Граница определяется правилами, а не таблицами

Сервис выделяют не потому, что существует таблица `wallet`, а потому, что есть отдельная бизнес-возможность с собственными инвариантами.

Для Wallet важны правила:

- баланс не уходит ниже допустимого значения;
- каждая финансовая операция отражается в immutable ledger;
- повторный `idempotency_key` не списывает деньги второй раз;
- `reserve → settle/release` образует контролируемый lifecycle;
- административная корректировка — отдельная аудируемая операция.

Именно Wallet должен проверять эти правила. Casino знает размер ставки и результат игры, но не изменяет поле balance напрямую.

## 2.2. Границы Realtime Casino Platform

| Сервис | Бизнес-ответственность | Source of Truth | Чего не должен делать |
|---|---|---|---|
| Identity | регистрация, login, sessions, роли и блокировка | User, Credentials, RefreshSession | хранить balance или правила игр |
| Wallet | деньги, ledger, reservations, settlement, idempotency | WalletAccount, LedgerEntry, Reservation | решать результат игры |
| Casino | комнаты, раунды, ставки, игровой результат, provably fair | Room, Round, Bet, GameResult | менять Wallet tables |
| Gateway | transport edge, auth edge, routing, WebSocket connections | только transport/ephemeral state | содержать игровую и финансовую бизнес-логику |

Gateway может проверить, что токен действителен, но решение `можно ли зарезервировать 1000 minor units` принимает Wallet. Gateway может передать `PlaceBet`, но правила стадии раунда проверяет Casino.

## 2.3. Почему нельзя читать чужую БД

Плохая схема:

```text
Casino → SELECT balance FROM wallet.accounts
Casino → UPDATE wallet.accounts SET balance = ...
```

Проблемы:

- Casino обходит инварианты Wallet;
- изменение схемы Wallet ломает Casino без изменения API;
- нельзя независимо развернуть или масштабировать сервисы;
- права к базе становятся слишком широкими;
- audit и idempotency легко обойти;
- локальная транзакция создаёт иллюзию согласованности между доменами.

Правильная схема:

```text
Casino → ReserveFunds(command) → Wallet
Wallet → проверяет balance и idempotency
Wallet → записывает Reservation + Ledger + Outbox в одной транзакции
Wallet → возвращает результат контракта
```

## 2.4. Идентификаторы и snapshots

Сервис может хранить внешний UUID:

```text
Casino.Bet.user_id → UUID пользователя из Identity
WalletAccount.user_id → UUID пользователя из Identity
```

Это не нарушает владение данными. Нарушение начинается, если Casino создаёт собственную изменяемую копию `User` и считает её правильной.

Для leaderboard Casino может хранить projection:

```text
user_id, nickname, avatar_version
```

Она обновляется по `user.profile_updated.v1`. При потере projection её можно перестроить. Пароль, refresh session и полный профиль в Casino не копируются.

## 2.5. Синхронная и eventual consistency

Синхронный вызов нужен, когда ответ необходим для продолжения текущей команды:

```text
PlaceBet
→ Casino обязан узнать, зарезервированы ли средства
→ синхронный ReserveFunds в Wallet
```

Событие подходит для реакции после уже совершившегося факта:

```text
bet.settled.v1
→ History projection
→ leaderboard
→ achievements
→ analytics
```

Событие не должно маскировать необходимость немедленного бизнес-решения. Команда спрашивает сервис-владелец: «выполни». Событие сообщает: «уже произошло».

## 2.6. Практическая фиксация контракта

Минимальный protobuf для финансовой команды:

```proto
syntax = "proto3";

package wallet.v1;

service WalletService {
  rpc ReserveFunds(ReserveFundsRequest) returns (ReserveFundsResponse);
}

message ReserveFundsRequest {
  string request_id = 1;
  string user_id = 2;
  string bet_id = 3;
  int64 amount_minor = 4;
  string currency = 5;
}

message ReserveFundsResponse {
  string reservation_id = 1;
  string status = 2;
  int64 available_balance_minor = 3;
}
```

`amount_minor` хранит целое количество минимальных денежных единиц. `request_id` становится частью идемпотентности. Контракт не раскрывает таблицы Wallet.

## 2.7. Инвариант на уровне БД

Даже правильный domain service полезно подкрепить ограничениями:

```sql
CREATE TABLE wallet_reservation (
    id UUID PRIMARY KEY,
    account_id UUID NOT NULL,
    bet_id UUID NOT NULL,
    idempotency_key UUID NOT NULL,
    amount_minor BIGINT NOT NULL CHECK (amount_minor > 0),
    status TEXT NOT NULL CHECK (status IN ('active', 'settled', 'released')),
    UNIQUE (idempotency_key),
    UNIQUE (bet_id)
);
```

Ограничения не заменяют бизнес-логику, но не позволяют двум конкурентным запросам незаметно создать дубликаты.

# 3. Типовые ошибки

### Ошибка: один сервис на каждую таблицу

Микросервис соответствует бизнес-возможности, а не одной ORM-модели.

### Ошибка: общая PostgreSQL без правил владения

Даже разные схемы в одной PostgreSQL требуют запрета прямого доступа к чужим таблицам и отдельных DB users/permissions.

### Ошибка: Gateway содержит бизнес-логику

Если Gateway решает размер payout, изменяет баланс или состояние Round, он становится центральным монолитом и bottleneck релизов.

### Ошибка: любое копирование данных запрещено

Разрешены внешние IDs, cache и projections. Запрещено превращать копию в независимый изменяемый Source of Truth.

### Ошибка: микросервисы автоматически лучше монолита

Микросервисы добавляют сетевые ошибки, eventual consistency, observability и сложность эксплуатации. Для небольшой системы модульный монолит может быть разумнее.

# 4. Связный ответ для собеседования

> Я определяю границу микросервиса по бизнес-возможности, данным и инвариантам. В Casino Platform Identity владеет пользователями и сессиями, Wallet — ledger и финансовым lifecycle, Casino — комнатами, раундами и ставками, а Gateway — только transport и realtime connections. Другой сервис может хранить внешний UUID или восстанавливаемую projection, но не изменяет чужие таблицы. Команды, для которых нужен немедленный результат, идут через явный API или gRPC, а уже произошедшие факты публикуются событиями. Такой подход уменьшает coupling и не даёт системе превратиться в distributed monolith.
