# 1. Что делает компонент микросервисом

> **Микросервис** — независимо изменяемый и развёртываемый компонент, который отвечает за отдельную бизнес-возможность, владеет её правилами и данными и взаимодействует через явные контракты.

Отдельный контейнер сам по себе не является микросервисом.

~~~text
Контейнер → способ запуска и изоляции процесса
Микросервис → архитектурная граница ответственности
~~~

Основные признаки:

1. отдельная бизнес-ответственность;
2. собственные правила и инварианты;
3. собственные данные как Source of Truth;
4. явные API/event contracts;
5. возможность независимо тестировать, изменять и развёртывать.

Сетевое взаимодействие может идти через gRPC, HTTP, Kafka и другие протоколы. Это не обязательно интернет: обычно используется внутренняя Docker- или Kubernetes-сеть.

Отказоустойчивость — цель, но не абсолютная гарантия:

~~~text
Wallet упал
→ Casino process продолжает работать
→ просмотр комнат может работать
→ принять новую ставку безопасно нельзя
~~~

---

# 2. Service boundary

> **Service boundary** — граница, определяющая, за что сервис отвечает, какие правила применяет и какими данными владеет.

Внутри границы:

~~~text
бизнес-ответственность
+ бизнес-правила и инварианты
+ собственные данные
~~~

На границе:

~~~text
gRPC/HTTP contracts
Kafka event schemas
WebSocket envelope
~~~

Пример Wallet:

~~~text
Ответственность → управление деньгами
Правила         → balance, ledger, reservation, settlement, idempotency
Данные          → WalletAccount, LedgerEntry, Reservation
Контракты       → ReserveFunds, SettleBet, ReleaseReservation
~~~

---

# 3. Bounded Context

> **Bounded Context** — ограниченная бизнес-область, внутри которой термины и правила имеют одно точное значение.

~~~text
Identity:
User = учётная запись, credentials, roles, sessions

Casino:
Player = участник комнаты и игрового процесса

Wallet:
Account = деньги, ledger, reservation
~~~

Все контексты могут использовать один **user_id**, но не обязаны иметь одинаковую модель пользователя.

Таблица БД не определяет Bounded Context. Controllers, services и repositories — технические слои, встречающиеся во всех контекстах. Они не описывают бизнес-возможность.

Фраза для запоминания:

> Wallet является отдельным Bounded Context, потому что финансовые термины и правила имеют внутри него точное значение, а Wallet владеет соответствующими данными и решениями.

---

# 4. Кто какими данными владеет

| Сервис | Постоянные бизнес-данные | Временные/технические данные |
|---|---|---|
| Identity | User, Credentials, RefreshSession, Role, Permission | auth cache при необходимости |
| Wallet | WalletAccount, LedgerEntry, Reservation, Settlement | локальные locks/cache |
| Casino | Room, RoomParticipant, Round, Bet, Tournament | RoomStateCache |
| Gateway | не владеет бизнес-сущностями | Connection registry, Presence, rate-limit counters |

Balance может быть полем WalletAccount или проекцией immutable ledger, а не отдельной сущностью.

Gateway владеет временным transport state. Потеря Gateway или Redis не должна уничтожить User, Bet, Round или Reservation.

---

# 5. Почему нельзя изменять чужую БД

Запрещённая схема:

~~~sql
UPDATE wallet_account
SET balance = balance - 1000
WHERE user_id = :user_id;
~~~

Проблемы:

- обход проверки достаточности средств;
- обход authorization и правил Wallet;
- отсутствие LedgerEntry и audit history;
- отсутствие idempotency;
- race conditions при конкурентных запросах;
- сильная связь Casino со схемой Wallet;
- избыточные DB permissions;
- невозможность независимо менять Wallet.

Правильная схема:

~~~text
Casino
→ Wallet.ReserveFunds(request_id, bet_id, amount_minor)
→ Wallet проверяет правила
→ Reservation + LedgerEntry + OutboxMessage
→ одна transaction
~~~

---

# 6. Как получить чужие данные

Другой сервис может использовать:

1. синхронный gRPC/HTTP query к владельцу;
2. Kafka events для построения local projection;
3. внешний UUID;
4. cache с TTL;
5. ранее полученный snapshot;
6. read-only projection.

Главное правило:

~~~text
Копию можно читать и перестраивать
Исходные данные изменяет только Source of Truth
~~~

---

# 7. Projection и Source of Truth

> **Projection** — локальная read-only модель, построенная из API response или событий владельца. Она может быть устаревшей и должна быть восстанавливаемой.

Пример:

~~~text
Identity Source of Truth:
user_id, nickname, avatar, status, credentials

Casino leaderboard projection:
user_id, nickname, avatar
~~~

Casino разрешено обновлять projection по событию **user.profile_updated.v1**.

Casino запрещено самостоятельно переименовывать пользователя и считать свою версию правильной. Команда изменения профиля направляется в Identity.

Projection не обязательно неполная. Главный признак — она не принимает самостоятельные бизнес-решения об исходных данных.

---

# 8. Инварианты Wallet ReserveFunds

Во время ReserveFunds Wallet обязан обеспечить:

- **amount_minor > 0**;
- совпадение currency;
- достаточный available balance;
- reserved средства нельзя потратить повторно;
- один **request_id** создаёт один business effect;
- одна **bet_id** не получает две активные reservations;
- конкурентные запросы не тратят одни средства дважды;
- Reservation, LedgerEntry и OutboxMessage фиксируются атомарно;
- допустимы только переходы:

~~~text
active → settled
active → released
~~~

Casino не получает деньги. Он получает подтверждение о созданной reservation.

---

# 9. Что должен делать Gateway

Gateway отвечает за:

- authentication edge;
- routing;
- rate limiting;
- WebSocket connections;
- transport envelope validation;
- преобразование внутренних ошибок;
- aggregation;
- correlation ID.

Gateway не должен:

- проверять финансовый balance;
- рассчитывать payout;
- изменять Round, Bet или Ledger;
- дублировать правила Identity, Casino и Wallet.

Если бизнес-логику поместить в Gateway:

~~~text
дублирование правил
→ согласованные релизы
→ центральный bottleneck
→ distributed monolith
~~~

# 10. gRPC command и Kafka event

Синхронный вызов нужен, когда результат необходим для продолжения текущей операции:

~~~text
Casino → Wallet.ReserveFunds
~~~

Casino не подтверждает ставку, пока Wallet не принял финансовое решение.

Kafka event подходит, когда факт уже зафиксирован:

~~~text
Casino commit Bet settlement
→ bet.settled.v1
→ leaderboard
→ achievements
→ analytics
~~~

Фраза для запоминания:

~~~text
Command → «выполни действие; результат нужен сейчас»
Event   → «это уже произошло; отреагируй»
~~~

Выбор определяется не скоростью, а необходимостью немедленного бизнес-решения.

# 11. Distributed monolith

> **Distributed monolith** — система из нескольких процессов, которые из-за сильной связанности нельзя независимо изменять, развёртывать и эксплуатировать.

Признаки:

- общая изменяемая БД;
- прямой доступ к чужим таблицам;
- общая domain/ORM model;
- один общий release всех сервисов;
- длинные обязательные синхронные цепочки;
- бизнес-логика в Gateway;
- падение одного dependency блокирует почти всю платформу;
- сервис невозможно отдельно запустить и протестировать.

Одна физическая PostgreSQL допустима на раннем этапе, если используются:

~~~text
отдельные схемы
+ отдельные DB users
+ запрет доступа к чужим таблицам
+ независимые миграции
+ явное владение
~~~

# 12. Domain validation и database constraints

Критичные правила защищаются на нескольких уровнях:

~~~text
Entity/domain service → понятная бизнес-ошибка
Wallet application    → idempotency и lifecycle
PostgreSQL            → защита от races и повреждения данных
~~~

Даже при использовании ORM миграции создают SQL constraints:

~~~sql
CREATE TABLE wallet_reservation (
    id UUID PRIMARY KEY,
    bet_id UUID NOT NULL,
    idempotency_key UUID NOT NULL,
    amount_minor BIGINT NOT NULL CHECK (amount_minor > 0),
    status TEXT NOT NULL
        CHECK (status IN ('active', 'settled', 'released')),

    UNIQUE (idempotency_key),
    UNIQUE (bet_id)
);
~~~

| Ограничение | Что защищает |
|---|---|
| **UNIQUE (idempotency_key)** | повтор команды не создаёт новый effect |
| **UNIQUE (bet_id)** | одна ставка не получает две reservations |
| **NOT NULL** | обязательные значения присутствуют |
| **CHECK (amount_minor > 0)** | сумма положительная |
| **CHECK status IN (...)** | нельзя сохранить произвольный статус |

Idempotency реализуется в сервисе-владельце — Wallet, а не в Gateway.

Wallet не проверяет существование Bet прямым запросом в Casino database. Он получает **bet_id** через контракт доверенного Casino service и гарантирует уникальность финансовой операции для этого ID.

# Главное выучить перед следующим занятием

1. Микросервис определяется бизнес-границей, а не контейнером.
2. Service boundary содержит ответственность, правила и данные.
3. Bounded Context задаёт точное значение бизнес-терминов.
4. Source of Truth изменяет данные; projection только отображает их.
5. Чужая БД недоступна напрямую.
6. Gateway не содержит финансовую и игровую логику.
7. gRPC command требует решения сейчас; Kafka event описывает совершившийся факт.
8. Outage isolation не означает, что все функции продолжат работать.
9. Общая изменяемая модель превращает сервисы в distributed monolith.
10. Domain validation дополняется database constraints.

## Короткий эталонный ответ

> В Casino Platform Identity, Wallet и Casino являются отдельными Bounded Contexts и Source of Truth для своих данных. Gateway отвечает только за transport edge. Сервисы не читают чужие таблицы: они используют gRPC для решений, необходимых прямо сейчас, и Kafka events для асинхронной реакции на уже зафиксированные факты. Локальные projections разрешены, если они read-only и восстанавливаемы. Финансовые инварианты защищаются Wallet domain logic, idempotency и PostgreSQL constraints.
