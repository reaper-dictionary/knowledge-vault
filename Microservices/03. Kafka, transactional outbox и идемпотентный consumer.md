# Kafka, transactional outbox и идемпотентный consumer

> [!info] Как пользоваться заметкой  
> Выучи определения и две гарантии: producer не теряет событие после commit благодаря outbox, consumer не повторяет бизнес-эффект благодаря `ProcessedEvent`.

---

# 1. Краткие определения — выучить

## Event

> **Event** — неизменяемое сообщение о факте, который уже произошёл: `bet.settled.v1`, `user.registered.v1`, `wallet.reservation.created.v1`.

## Command

> **Command** — просьба выполнить действие: `ReserveFunds`, `PlaceBet`, `BlockUser`. Команда может быть отклонена; событие описывает уже произошедший факт.

## Producer и consumer

> **Producer** публикует сообщения в Kafka. **Consumer** читает сообщения и выполняет локальную реакцию.

## Topic и partition

> **Topic** — именованный поток сообщений. **Partition** — упорядоченная часть topic; Kafka гарантирует порядок только внутри одной partition.

## Consumer group

> **Consumer group** — группа экземпляров одного логического consumer, между которыми Kafka распределяет partitions. Одну partition одновременно обрабатывает один consumer внутри группы.

## Offset

> **Offset** — позиция сообщения внутри partition. Commit offset сообщает Kafka, до какого места consumer успешно продвинулся.

## At-least-once delivery

> **At-least-once** — сообщение не должно потеряться, но может быть доставлено повторно. Поэтому consumer обязан быть идемпотентным.

## Transactional outbox

> **Transactional outbox** — запись business data и сообщения для публикации в одной локальной транзакции БД; отдельный publisher позже отправляет outbox message в Kafka.

## Idempotent consumer

> **Idempotent consumer** — consumer, который при повторной доставке того же `event_id` не повторяет бизнес-эффект.

## DLQ

> **Dead Letter Queue** — отдельный topic для сообщений, которые не удалось обработать после ограниченного числа попыток. DLQ не исправляет ошибку автоматически.

## Schema evolution

> **Schema evolution** — контролируемое изменение event contract с правилами совместимости и явной версией.

## Главная схема

```text
Wallet transaction:
Reservation + LedgerEntry + OutboxMessage
                    ↓ commit
Outbox publisher → Kafka → consumer
                           ↓
                 ProcessedEvent + local change
                    одна transaction
```

# 2. Подробные объяснения — понять

## 2.1. Почему прямой publish после commit опасен

Плохая схема:

```text
1. Wallet commit Reservation
2. процесс падает
3. Wallet не успевает publish reservation.created
```

Бизнес-факт существует, а событие потеряно. Обратный порядок тоже опасен:

```text
1. publish event
2. transaction rollback
```

Consumer увидит событие о факте, которого нет в Source of Truth.

Outbox решает dual-write problem одной локальной транзакцией.

## 2.2. Таблица outbox

```sql
CREATE TABLE outbox_message (
    event_id UUID PRIMARY KEY,
    topic TEXT NOT NULL,
    event_name TEXT NOT NULL,
    event_version INTEGER NOT NULL,
    aggregate_id UUID NOT NULL,
    correlation_id UUID NOT NULL,
    payload JSONB NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ NULL,
    attempts INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX ix_outbox_unpublished
    ON outbox_message (occurred_at)
    WHERE published_at IS NULL;
```

Outbox хранится в той же PostgreSQL, что и бизнес-данные сервиса. Общая outbox database для всех сервисов снова создаст coupling.

## 2.3. Одна транзакция в async SQLAlchemy

```python
from datetime import UTC, datetime


async def reserve_funds(session, reservation, ledger_entry, event):
    async with session.begin():
        session.add(reservation)
        session.add(ledger_entry)
        session.add(
            OutboxMessage(
                event_id=event.event_id,
                topic="wallet.events",
                event_name="wallet.reservation.created",
                event_version=1,
                aggregate_id=reservation.account_id,
                correlation_id=event.correlation_id,
                payload=event.payload,
                occurred_at=datetime.now(UTC),
            )
        )
```

Если транзакция откатится, не появится ни Reservation, ни LedgerEntry, ни OutboxMessage.

## 2.4. Publisher и блокировка строк

Несколько publisher instances не должны отправлять одну строку одновременно. Для PostgreSQL подходит выборка:

```sql
SELECT *
FROM outbox_message
WHERE published_at IS NULL
ORDER BY occurred_at
FOR UPDATE SKIP LOCKED
LIMIT 100;
```

После успешного Kafka acknowledgement publisher отмечает `published_at`. Между publish и отметкой процесс всё равно может упасть, поэтому duplicate возможен. Outbox даёт at-least-once, а не магическое exactly-once для всей бизнес-системы.

## 2.5. Структура события

```json
{
  "event_id": "a3e8...",
  "name": "bet.settled",
  "version": 1,
  "occurred_at": "2026-08-07T12:00:00Z",
  "aggregate_id": "bet-uuid",
  "correlation_id": "request-uuid",
  "payload": {
    "bet_id": "bet-uuid",
    "user_id": "user-uuid",
    "game": "crash",
    "stake_minor": 1000,
    "payout_minor": 1750
  }
}
```

Событие содержит факт, нужный consumers, но не внутренний ORM dump и не secrets. `event_id` отвечает за дедупликацию, `aggregate_id` — за routing/order, `correlation_id` — за трассировку.

## 2.6. Partition key и порядок

Если порядок важен для одной ставки:

```text
partition key = bet_id
```

Тогда события одной Bet попадут в одну partition:

```text
bet.placed → bet.settled → bet.closed
```

Kafka не гарантирует глобальный порядок между разными partitions. Нельзя проектировать consumer так, будто все события платформы идут строго последовательно.

## 2.7. Идемпотентный consumer

Техническая таблица:

```sql
CREATE TABLE processed_event (
    consumer_name TEXT NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer_name, event_id)
);
```

Обработка должна поместить отметку и локальный бизнес-эффект в одну транзакцию:

```python
from sqlalchemy import text


async def handle_bet_settled(session, event):
    async with session.begin():
        inserted = await session.execute(
            text("""
                INSERT INTO processed_event (consumer_name, event_id)
                VALUES (:consumer, :event_id)
                ON CONFLICT DO NOTHING
                RETURNING event_id
            """),
            {"consumer": "leaderboard-v1", "event_id": event.event_id},
        )

        if inserted.scalar_one_or_none() is None:
            return

        await apply_score_change(session, event.payload)
```

Offset commit выполняется только после успешного commit БД. Если процесс упадёт раньше offset commit, Kafka доставит event снова, а `processed_event` остановит повторный effect.

## 2.8. Retry и DLQ

Ошибки делятся на:

```text
transient → PostgreSQL временно недоступна → retry с backoff
permanent → неизвестная version/невалидный payload → DLQ и alert
bug → exception в коде → ограниченный retry, затем DLQ и расследование
```

Бесконечный retry одного poison message блокирует partition. Но отправка в DLQ без alert и процедуры replay просто скрывает потерянную обработку.

## 2.9. Где Kafka не нужна

Не следует отправлять каждый realtime tick Crash через Kafka только потому, что Kafka уже есть. Высокочастотный эфемерный broadcast лучше вести через WebSocket/Redis Pub/Sub. Kafka используется для значимых надёжных фактов:

- bet placed/settled;
- wallet reservation/settlement;
- user registered/blocked;
- achievement granted;
- audit-relevant operations.

# 3. Типовые ошибки

### Ошибка: событие называется как команда

`CreateWallet` — команда. `wallet.created.v1` — уже произошедший факт.

### Ошибка: commit offset до БД

При падении после offset commit, но до commit БД сообщение будет потеряно для consumer.

### Ошибка: надеяться, что Kafka никогда не повторяет сообщения

Rebalance, retry и падение между двумя commits создают повторную доставку.

### Ошибка: считать outbox exactly-once

Outbox предотвращает потерю между DB commit и publish, но повтор publish всё ещё возможен.

### Ошибка: использовать user ID как Prometheus label

IDs нужны в event/log/trace, но не в metric labels с ограниченной cardinality.

### Ошибка: удалять неизвестные события без сигнала

Неизвестная version должна приводить к контролируемой ошибке, DLQ и alert, а не к silent drop.

---

# 4. Связный ответ для собеседования

> Kafka обычно доставляет сообщения at-least-once, поэтому producer и consumer должны учитывать дубликаты. Producer записывает business data и OutboxMessage в одной PostgreSQL-транзакции; отдельный publisher отправляет записи в Kafka. Consumer в одной локальной транзакции создаёт уникальный ProcessedEvent и применяет изменение, а offset подтверждает только после commit. Partition key выбирается по aggregate, если важен порядок его событий. Временные ошибки повторяются с backoff, постоянные после ограниченного числа попыток идут в DLQ с alert и процедурой replay.
