# Сущности и моделирование данных

# 1. Краткие определения — выучить

## Entity

> **Entity** — объект с собственной идентичностью и жизненным циклом. Поля меняются, но `id` остаётся тем же.

## Value Object

> **Value Object** — объект без отдельного `id`, определяемый значениями полей и обычно неизменяемый.

Примеры: `Money(amount_minor, currency)`, адрес, диапазон дат.

## Aggregate и Aggregate Root

> **Aggregate** — группа объектов, согласованность которых защищается вместе. **Aggregate Root** — единственная точка изменения aggregate извне.

## Invariant

> **Invariant** — правило, которое остаётся истинным после каждой успешной операции.

## State machine

> **State machine** — допустимые состояния Entity и переходы между ними.

## ORM model

> **ORM model** — описание хранения объекта в таблице. Это persistence model, а не бизнес-правила.

## Constraint

> **Constraint** — правило базы данных: `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, `FOREIGN KEY`.

# 2. Как находить сущности и поля

Сначала записывают бизнес-действия:

~~~text
создать заказ → подтвердить заказ → отменить заказ
~~~

Существительные дают кандидатов в объекты, глаголы — их поведение. Не каждый объект должен стать таблицей.

Объект обычно является Entity, если у него есть:

- собственный `id`;
- изменяемое состояние;
- жизненный цикл;
- ссылки из других объектов;
- правила для конкретного экземпляра.

Если важны только значения и объект можно заменить целиком, это чаще Value Object.

До проектирования полей определяется сервис — Source of Truth. Другие сервисы хранят внешний UUID, snapshot или projection, но не создают foreign key в чужую БД.

## Группы полей

| Категория | Примеры |
|---|---|
| Идентичность | `id` |
| Бизнес-данные | `name`, `amount_minor`, `currency` |
| Состояние | `status`, `version` |
| Связи | `owner_id`, `order_id` |
| Надёжность | `idempotency_key`, `operation_id` |
| Время | `created_at`, `updated_at`, `completed_at` |

Каждое поле должно участвовать в сценарии, правиле, запросе или аудите. Поля «на будущее» не добавляют.

Состояние изменяют методами, а не свободной записью:

~~~python
order.confirm()
order.cancel()
~~~

Метод проверяет текущий status, invariants и допустимость перехода.

# 3. Алгоритм создания сущности

1. Записать бизнес-сценарии и команды.
2. Определить сервис-владелец.
3. Решить: Entity, Value Object, Aggregate или projection.
4. Выписать только необходимые поля и типы.
5. Сформулировать invariants обычными предложениями.
6. Описать состояния и разрешённые переходы.
7. Создать методы, выполняющие переходы.
8. Определить indexes и constraints.
9. Создать ORM mapping и миграцию.
10. Проверить миграцию и протестировать invariants.

Минимальная карточка проектирования:

~~~text
Name and owner
Fields and types
Invariants
State transitions
Indexes and constraints
Commands and queries
~~~

Критичное правило защищают на двух уровнях:

~~~text
Domain → понятная бизнес-ошибка
Database → защита от race condition и повреждения данных
~~~

# 4. Типовые ошибки

### Делать Entity из каждого DTO

Request, response, event и cache entry могут не быть бизнес-сущностями.

### Хранить деньги в `float`

Используются целые minor units и currency.

### Проверять invariant только в handler

Правило должно защищаться Entity/domain service, а критичное правило — также constraint базы.

### Создавать foreign key между сервисами

Между разными БД хранится внешний UUID без межсервисного foreign key.

### Путать `request_id` и `idempotency_key`

Первый связывает логи, второй предотвращает повторный business effect.

### Разрешать любой переход status

Переходы задаются state machine и выполняются методами.
